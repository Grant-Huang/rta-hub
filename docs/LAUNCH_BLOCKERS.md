# 上线阻断项台账

> **这份文件是什么**：几项「不核实就不能上线」的事的**核实台账**——每一项记清楚
> 当前取值、来源、错了会怎样、怎么核、谁负责、什么时候核的、依据是什么。
>
> **与 [PRE_LAUNCH_CHECKLIST.md](./PRE_LAUNCH_CHECKLIST.md) 的区别**：检查清单是全量的
> A–I 几十项待办；这份只收**阻断项**，并且带核实历史。清单回答「还有什么要做」，
> 这份回答「这个数字凭什么是对的、谁在什么时候确认的」。
>
> **它不只是文档。** 清单里的每一项在代码里都有对应的闸门
> （`src/app/launch-gates.ts`）：生产环境有未核实的阻断项时**服务拒绝启动**。

---

## 0. 为什么这几项要单独拎出来

它们有一个共同点：**错了不会报错，只会安静地给出错误的结果。**

税率错了照样出报价单，只是金额错了；NKBA 净空错了照样判方案合规，只是判错了。
编译不会失败，测试不会红，监控看不出来——等发现的时候，错的东西已经发给客户和
橱柜公司了。

这类问题唯一可靠的防线是**在它产出结果之前拦住**，所以做成了启动闸门而不是待办事项。

**阻断与否的判断标准**：错了会不会**安静地产出错误的对外结果**。

- 税率错 → 报价单金额错，且这份金额同时发给客户和公司 → 阻断
- NKBA 净空错 → 合规方案被判不合规，或不合规方案被放行 → 阻断
- 鉴权没做 → 任何人可冒充账号读取他人 PII → 阻断
- 线索费率没定 → 会向公司收一笔没谈过的钱 → 阻断
- `GenericCatalog` 未核实 → 代码已如实降级标注为占位数据，不冒充行业数据 → 只告警
- 留存清除未接 → 数据留超期，是合规问题但不产出错误结果 → 只告警

## 2. 怎么用

```bash
pnpm gates        # 查看当前状态；有阻断项未通过时退出码为 1，可直接用于部署门禁
```

核实完一项，在环境里写**核实日期**：

```bash
VERIFIED_TAX_RATES=2026-08-06
```

### 为什么记日期而不是 `true`

核实过不等于永远有效。各省税率会改（NS 2025-04-01 由 15% 降到 14%，我们的税表里
就是两条记录），NKBA 指南也有修订历史。日期能让闸门在**过了复核周期后自动变回待办**；
写 `true` 的话，三年后没人知道那个 `true` 是什么时候按下的。

代码只接受 `YYYY-MM-DD`，`true` 会被当成未核实。

### 明知故犯的逃生口

确实要在某项未核实的情况下上线，必须**逐项**声明：

```bash
LAUNCH_GATES_ACKNOWLEDGED=A6,G4
```

刻意不做成一个总开关——一把全关等于这套机制不存在。写进去的 id 会出现在启动日志里。

## 3. A1/A2　各省税率与生效日期

**代码位置**：`src/pricing/tax.ts` 的 `SEED_TAX_RULES`

**当前取值**（13 个省/地区，左闭右开区间 `[effectiveFrom, effectiveTo)`）：

| 省/地区 | 组成 | 税率 |
|---|---|---|
| ON | HST | 13% |
| NS | HST | 15% → **14%（2025-04-01 起）** |
| NB / NL / PE | HST | 15% |
| BC | GST 5% + PST 7% | 12% |
| MB | GST 5% + PST 7% | 12% |
| SK | GST 5% + PST 6% | 11% |
| QC | GST 5% + QST 9.975% | 14.975% |
| AB / NT / NU / YT | GST | 5% |

**错了会怎样**：报价单上的税额与总价直接错。这份金额同时发给客户和橱柜公司，
并写进不可变的 `Quote` 快照与 7 年留存的审计记录——事后改不了，只能作废重开。

**怎么核**：

1. 逐省对照 [Canada Revenue Agency 的 GST/HST 税率页](https://www.canada.ca/en/revenue-agency/services/tax/businesses/topics/gst-hst-businesses/charge-collect-which-rate.html)；
2. PST/QST 要另查各省税务厅（BC、SK、MB 的 PST 与 QC 的 QST 不归 CRA 管）；
3. **重点核 QC 的 9.975%**——它不是整数百分比，代码里按 1/10000 精度算
   （`percentOf`），核实时要确认是「9.975% 单独计征」而不是复合计征；
4. 确认 NS 的 14% 生效日期，以及是否还有其他省在计划期内变更。

**验收标准**：13 个省全部有出处链接与查询日期；任何一条与代码不符的，改代码后
重跑 `pnpm test`（税率相关用例在 `test/pricing.test.ts`）。

## 4. A6　NKBA 人体工程净空　⚠️ 目前最不放心的一项

**代码位置**：`src/layout/ergonomics.ts` 的 `CLEARANCE`

这些是**硬约束**——不参与目标函数的权衡，违反即 `acceptable = false`，方案不出图、
报价接口返回 409。所以数值错了，两个方向都会出事：

- **偏大** → 本来合规的方案被判不合规，客户拿不到方案，我们还以为是算法不行；
- **偏小** → 灶台旁没处放热锅这类方案被放行，发给客户和公司。

两个方向都不会报错，也不会被测试发现——测试断言的是「代码按这些常量正确判断」，
不是「这些常量本身对不对」。

**当前取值——逐条待核**：

| 常量 | 当前值 | 用途 | 严重度 |
|---|---|---|---|
| `sinkLandingPrimary` | 24" | 水槽一侧台面工作区 | blocking |
| `sinkLandingSecondary` | 18" | 水槽另一侧 | blocking |
| `cooktopLandingPrimary` | 15" | 灶具一侧落台区（放热锅，**安全项**） | blocking |
| `cooktopLandingSecondary` | 12" | 灶具另一侧 | blocking |
| `refrigeratorLanding` | 15" | 冰箱把手侧落台区 | blocking |
| `microwaveLanding` | 15" | 微波炉落台区 | advisory |
| `dishwasherToSinkMax` | 36" | 洗碗机边缘距水槽最近边上限 | blocking |
| `dishwasherStanding` | 21" | 洗碗机一侧站立空间 | blocking |
| `continuousPrepSurface` | 36" | 连续备餐台面至少一段 | blocking |
| `workTriangleLegMin` | 4 ft | 工作三角单边下限 | advisory |
| `workTriangleLegMax` | 9 ft | 工作三角单边上限 | advisory |
| `workTriangleTotalMax` | 26 ft | 工作三角三边之和上限 | advisory |

**来源现状**：取自 NKBA（National Kitchen & Bath Association）厨房规划指南的**公开
整理版本**，**没有对照官方原文逐条核实过**。这是我们目前最薄弱的一处依据。

**怎么核**：

1. 取 NKBA 现行版《Kitchen Planning Guidelines with Access Standards》**原文**
   （31 条指南，需购买或通过会员渠道获取）——公开整理版常有简化和过时；
2. 逐条对照上表，记录每个数值对应的**指南编号**（例如 Guideline 5 是备餐台面）；
3. 注意区分 NKBA 的 **"recommended" 与 "code requirement"**——我们把它们全做成了
   blocking，如果原文里某条只是建议，应当降为 advisory；
4. 与加拿大本地实践对照：NKBA 是美国组织，部分数值在加拿大的 National Building Code
   下可能有差异，尤其是**灶具净空这类涉及防火的**；
5. 单位确认：原文若给的是毫米，换算后要与我们的 1/4" 量化网格对齐。

**验收标准**：

- 每个常量都有指南编号与页码；
- 每个常量都标明是 requirement 还是 recommendation，并与代码里的 `severity` 一致；
- 涉及防火/安全的项（灶具两侧）另附加拿大本地依据；
- 改动后重跑 `test/layout-quality.test.ts`，并**人工复核几个真实户型的判定结果**——
  数值一改，原本 acceptable 的方案可能整批翻转。

## 5. A4　`GenericCatalog` 价格区间的数据来源

**代码位置**：`src/app/seed.ts` 的 `genericCatalog`

**用途**：冷启动时，还没有公司入驻/被 `@`，客户仍能拿到一份 `EstimateDraft`
（FR-10）。区间就是从这份目录来的。

**为什么只告警不阻断**：代码已经如实处理了「来源未核实」这件事——
`catalogSourceVerified` 为假时，预估文案会标注为占位数据，不冒充行业数据。
系统的行为是诚实的，所以不拦启动；但一直不定案，冷启动预估的可信度就一直立不住。

## 6. G4　线索费率定案

**代码位置**：`LEAD_FEE_CAD` 环境变量（默认 45.00 CAD），`src/billing/lead-events.ts`

**错了会怎样**：费率没定就开始计费，等于向入驻公司收一笔他们没同意过的钱。
计费事件是不可变的，还有 14 天争议窗口和 7 年留存——收错了要一条条退。

**待决**：参考 Thumbtack 同类品类 $10–100+ 的量级，但橱柜单均金额高（一整套通常
大几千到几万加币），费率结构可能需要与品类均价挂钩，而不是套用其他家装品类的定价。

**验收标准**：费率写进与首批入驻公司的合同，且与代码里的 `LEAD_FEE_CAD` 一致。

## 7. E1　生产级鉴权

**代码位置**：`src/server.ts` 的 `requireAccount`；整站口令在 `src/app/site-gate.ts`

**当前状态**：三道锁叠加——整站访问口令（`SITE_PASSWORD`）→ `X-Account-Id` 账号头
→ `ADMIN_TOKEN` 运营令牌。

**仍然不够**：`X-Account-Id` **不做校验**。整站口令**后面**的人仍可把这个头改成
任意账号 id，读取他人的姓名、邮箱与户型图。整站口令买到的是时间，不是安全。

**验收标准**：真正的登录态（邮箱验证码或 OAuth + 会话令牌）+ 四类角色的权限模型
（消费者 / trade / 公司运营 / 平台管理员）。
