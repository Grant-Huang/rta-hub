# 产品目录模型 —— 通用目录、商家规格、以及两者的关系

> 状态：第 2 节（能力标签）**已实现**（`src/spec/capabilities.ts`，M5-2）；
> 其余部分仍是设计稿。本文回答四个问题：
> 1. 报价背后到底基于什么清单？这份清单怎么固定下来？
> 2. 换一种门板花色，客户能不能看到价格差？
> 3. 新商家入驻时，是直接用商家自己的规格，还是做映射表？
> 4. 商家之间的**设计差异**（连体/分体 pantry、42" vs 39" 吊柜、需要叠装的高层高）
>    怎么建模？
>
> 前三个是"数据放在哪"的问题，第四个是"能不能建模"的问题——而第四个才是
> 真正决定架构的那个。先回答第四个，前三个的答案就是它的推论。

---

## 0. 先说结论

| 问题 | 结论 |
|---|---|
| 报价基于什么 | **商家的 `ProductSpecVersion`**（型号表 + 价格矩阵），发布后不可变。这份清单已经存在且已经是报价的唯一来源 |
| 通用目录的角色 | **只用于冷启动预估**（FR-10），**永远不产生正式报价**。它不是"商家规格的默认值" |
| 换花色比价 | 在报价清单里加一张**同方案换价格组**的对比表。逐行重算，不是给总价乘一个系数 |
| 商家规格怎么接 | **直接用商家自己的型号码定价，不做通用码映射**；另建一层**能力标签**（capability）供排布算法使用 |
| 设计差异 | 靠能力标签 + 组合规则（`ModuleComposition`）建模，**不靠型号码约定** |

一句话：**编码不映射，能力才映射。**

---

## 1. 为什么不能做「通用码 ↔ 商家码」的映射表

这是最容易想到的方案，也是错的。理由不是工程量，是**语义不守恒**。

### 1.1 同一个"通用码"在不同商家指的不是同一件东西

用户举的例子精确地说明了问题：

> 有的商家 pantry 上下柜是**连体**的，有的是**分离**的。

假设通用码有一个 `PANTRY84`。映射到 A 商家是一个 84" 的整柜（一个 SKU、一个价格、
一扇通高门）；映射到 B 商家是 `PC1842 + PC1842` 两个柜叠装（两个 SKU、两个价格、
中间有一条**看得见的横缝**，正视图必须画出来，且需要一套连接件）。

这两者：
- **件数不同** → BOM 行数不同；
- **价格构成不同** → 不是"一个数换一个数"；
- **外观不同** → 图纸不一样；
- **安装不同** → 一个要连接件，一个不要。

一张映射表只能存"A 的 X 对应 B 的 Y"。它存不下"A 的一个变成 B 的两个，而且中间多
一条缝、多一包五金"。硬塞的结果是映射表里出现 `PANTRY84 → [PC1842, PC1842] + 连接件`
这种条目——那已经不是映射表了，那是**组合规则**，只是被写成了映射表的样子。

### 1.2 尺寸档位不是"最接近的那个"

> 有的商家有 42 寸高的墙柜，有的最高只有 39 寸。

如果做映射，`W3042`（通用）在只有 39" 的商家那里映射到什么？

- 映射到 39"：**默默改了尺寸**。客户看到的图是 42" 的，收到的柜子是 39"，
  顶上多出 3" 的缝。这是最坏的一种错——它不报错，它只是错。
- 映射到"无"：那么这个商家在这个户型下**根本报不了价**，而事实上他完全可以做
  （用 39" 吊柜 + 3" 的填充/顶线，或者换一个层高档位重排）。

正确的做法是：**层高是输入，吊柜高度是求解结果**。系统不该先选一个"通用高度"再去
各家找对应品，而该把「天花板 96"、吊柜底边 54"、要留 6" 顶线空间」这组约束交给
**每家自己的高度档位表**去解。A 家解出 42"，B 家解出 39" + 更高的顶线，两家都对，
两个方案都能报价、都能画图。

`pickWallCabinetHeight()` 已经是这个形状了（传入 `ceilingHeight` 和该公司的
`available` 高度数组）。要做的是把这条原则**贯彻到所有维度**，而不是引入一层通用码
把它破坏掉。

### 1.3 结论

> **报价与出图，一律直接使用商家自己的 `ModuleSpec.code` 与价格矩阵。
> 系统内部不存在"通用型号码"这个东西。**

那排布算法怎么办？它总得知道"这个柜子是干什么用的"。答案见下一节。

## 2. 能力标签（Capability）—— 排布算法真正需要的那一层

排布算法不需要知道"这是 B30 还是 NW-BS30"。它需要知道的是：

- 这个柜子**能不能放水槽**（要预留下水、门后不能有抽屉）；
- 这个柜子**是不是抽屉柜**（高频区优先）；
- 这个柜子**是不是给某个家电配套的**（冰箱上柜、烤箱高柜、抽油烟机位）；
- 它的**宽度/高度/进深有哪些离散档位**；
- 它**能不能和别的柜子叠装**。

这些是**能力**，不是编码。能力可以跨商家对齐，编码不能。

### 2.1 数据结构

```ts
/** 型号能力标签。排布算法只读这个，不读 code。 */
export interface ModuleCapabilities {
  /** 承载什么功能。一个型号可以有多项（如"水槽柜 + 假抽屉面"）。 */
  roles: ModuleRole[];
  /** 给哪种家电配套。非配套柜为空。 */
  servesAppliance?: ApplianceKind;
  /** 能否作为叠装的下段 / 上段。 */
  stacking?: { asLower: boolean; asUpper: boolean };
  /** 这个型号本身是不是"上下连体"（连体的不需要叠装，也不该被拆开）。 */
  monolithic?: boolean;
}

export type ModuleRole =
  | "doorStorage"      // 门板柜
  | "drawerStorage"    // 抽屉柜
  | "sinkBase"         // 水槽柜
  | "cooktopBase"      // 灶台下柜（台面开孔、抽屉要避让）
  | "applianceHousing" // 家电柜（烤箱/微波塔）
  | "cornerAccess"     // 转角（斜切/盲角）
  | "openDisplay"      // 开放格/酒格
  | "trim";            // 填缝、收口、踢脚、顶线
```

### 2.2 能力从哪来

三个来源，按可信度排序：

1. **商家在规格导入时直接声明**（最可信）。`ModuleSpec.capabilities`。
2. **从脸型模板反推**（次可信）。`F7_FALSE_FRONT_DOUBLE` 只可能是水槽柜；
   `F6_DRAWER_STACK` 一定是抽屉柜。这条复用 `matchFaceTemplate` 已经定好的语义，
   不另起一套规则。
3. ~~**从型号码前缀猜**~~ —— **不做**。那正是这一层要消除的东西。

关键规则与 FR-2 的「零静默失败」一致：

> **推不准的能力不能直接进规格库。** 走待确认队列，由人（商家运营）确认后才生效。
> 一个把水槽柜误判成普通地柜的规格库，会让每一版方案的水槽都排错位置——
> 而且不报错，只是一直错。

**实现后发现的一处**：脸型能告诉我们「这是个家电柜（中间开洞）」，但告诉不了
「配哪种家电」——而开洞高度、周边配件都取决于后者。按 `OC` 前缀猜 oven cabinet
恰恰是被否掉的那条路。所以 `applianceHousing` 而没有 `servesAppliance` 的型号
一律标为低可信、进待确认队列；试点公司的 `OC3084` 则在 seed 里**显式声明**
（走第 1 档可信度）。

### 2.3 这样一来，「连体 vs 分体 pantry」就不需要映射了

| | A 商家（连体） | B 商家（分体） |
|---|---|---|
| 型号 | `PANTRY1884`（一个） | `PC1842` × 2（叠装） |
| 能力 | `roles:["doorStorage"], monolithic:true` | `roles:["doorStorage"], stacking:{asLower:true,asUpper:true}` |
| 排布器要的 | 「给我一个 18" 宽、84" 高的储物高柜」 | 同左 |
| 排布器拿到的 | 1 个 placement | 2 个 placement + 1 条水平接缝 |

排布算法问的是同一个问题，两家各自用自己的方式回答。没有中间层，也就没有语义损失。

### 2.4 这一层顺手修掉了一个已经存在的 bug 类（M5-2 实现记录）

改造前 `layout/generate.ts` 里散着这样的判断：

```ts
/^(\d)DB/i.test(m.code)            // 是不是抽屉柜
/^(BPO|TDC|BWB)/i.test(m.code)     // 是不是"有功能的窄柜"
m.type === "sinkBase"              // 是不是水槽柜
```

第二家试点公司用 `NW-` 前缀命名，前两条正则**一个也命不中**。后果不是报错，
而是「高频区优先抽屉柜」「功能性窄柜不罚分」这两条规则在那家公司上**静默失效**——
方案照样出，只是变差了，没有任何地方会提示。

这与「@ 路由不靠 LLM 猜公司名」是同一条原则：**靠字符串猜语义，换一家就崩。**

测试里有一条专门盯这个：把整套规格改个前缀，排出来的柜型构成必须逐位一致。

## 3. 叠装吊柜（层高高的房子）

> 现在的房子都比较高，如果上柜高度达到 51 寸，那么肯定需要拼。

这是 §2 的一个具体实例，但它有自己的难点，单列。

### 3.1 什么时候需要叠装

吊柜可用高度 = `ceilingHeight − 54"（吊柜底边）− 顶线预留`。

- 96" 层高 → 可用 ~36"，单柜能做；
- 108" 层高 → 可用 ~48"，如果商家最高只有 42"，**要么留 6" 空当，要么叠装**；
- 120" 层高 → 可用 ~60"，一定要叠装。

### 3.2 叠装是一个**求解**，不是一个开关

给定目标高度 H 和商家的高度档位集合 `{12, 15, 18, 24, 30, 36, 42}`，要找一组
高度使得：

```
Σ hᵢ + (n−1) × 接缝损耗 = H        // 精确匹配，或落在可接受的余量内
```

约束与偏好：

- **硬**：每一段都必须是该商家真实存在的档位（FR-8 同源原则）；
- **硬**：上段必须 `stacking.asUpper`，下段必须 `stacking.asLower`；
- **偏好**：段数越少越好（缝少、装得快、便宜）；
- **偏好**：**下段更高**（视觉上重心在下，且常用高度在下段）；
- **偏好**：同一面墙上的横向接缝**高度一致**（否则正视图上是一条锯齿线，很难看）。

最后一条是关键的美观约束，属于 FR-4.1 的**软约束**层。它跨柜体，所以不能在
"给每个柜子单独求解"的循环里做——必须**先在墙段层面定下接缝高度，再给每个柜子求解**。

### 3.3 解不出来的时候要如实说

如果 `H = 48"` 而档位只有 `{30, 36, 42}`，且不允许留缝：
- `42 + 6`？没有 6" 的档位 → 无解；
- 那就退回「42" 单柜 + 6" 顶线加高」，并**在解释里说清楚**：
  「你家层高 108"，这家最高的吊柜是 42"，顶上 6" 用加高顶线收口。
  如果想做到顶，需要选支持叠装的商家。」

不能静默地把 48" 变成 42"。这与 §1.2 是同一条原则。

## 4. 报价的唯一数据源

### 4.1 现状（已实现，本节是确认不是改动）

报价**已经**基于一份固定的清单，且它已经是不可变的：

```
ProductSpecVersion (status: published, 发布后不可变)
  ├── ModuleSpec[]        型号：code / type / 宽高深档位 / assemblyOptions
  ├── PriceGroup[]        价格组：A / B / …
  ├── DoorStyle[]         门板样式 → priceGroupId
  ├── PriceMatrixEntry[]  (moduleId × priceGroupId) → listPrice
  ├── HardwareOption[]    五金加价
  ├── AccessoryOption[]   配件加价
  ├── DiscountRule[]      折扣
  └── ShippingRule[]      运费
```

- 报价时 `Quote` 记录 `specVersionId` 并**快照价格**（§3.6），商家事后改价不影响
  已出的报价；
- 价格矩阵有洞时抛 `PRICE_MATRIX_HOLE`，**不回退到任何默认值**；
- 后台改价 = 建新草稿 → 发布新版本，旧版本仍在。

所以"后台可以改，但每次算报价都基于这份清单"这一条**已经成立**。需要补的是下面两点。

### 4.2 通用目录的定位要写死：只能预估，不能报价

`GenericCatalog` 现在是 FR-10 冷启动用的价格区间（`typicalPriceRange`），
数据是占位的（`sourceNote` 已如实标注，且是上线阻断项 A4）。

必须在文档和代码里明确：

> **通用目录永远不产生 `Quote`，只产生 `EstimateDraft`。**
> 它没有型号码、没有价格矩阵、没有商家——它给的是一个区间和一句"实际价格以
> 具体商家报价为准"。

这条已经是实现的行为，但从没被写成一条规则。写下来是为了防止将来有人"顺手"
拿通用目录去补一个缺货商家的价格洞。

### 4.3 哪些物料的价格随门板花色变，哪些不变

这个区分现在**是错的**，必须修。

价格矩阵是 `(moduleId × priceGroupId)`，而 `priceGroupId` 来自门板样式。这意味着
**每一个型号**的价格都随花色变——包括塑料地脚。但：

| 类别 | 随花色变？ | 为什么 |
|---|---|---|
| 柜体（含门） | ✅ | 门板就是花色本身 |
| 填缝条 `filler` | ✅ | 要与门同色，否则墙角一条白边 |
| 收口板 `panel` | ✅ | 同上，这是它存在的理由 |
| 踢脚板 `toeKick` | ✅ | 贴面要同色 |
| 顶线 `crown` | ✅ | 同色 |
| **塑料地脚 `leg`** | ❌ | 藏在踢脚板后面，**没人看得见**。黑色塑料件，一个价 |
| 五金 | ❌ | 已经是独立的 `HardwareOption`，不走价格矩阵 |

所以需要给 `ModuleSpec` 加一个字段：

```ts
/**
 * 这个型号的价格是否随门板价格组变化。
 *
 * 缺省 true（绝大多数件都要同色）。塑料地脚、连接件这类**看不见的**
 * 结构件设为 false——给它们编一个"高级花色版"的价格是凭空加价。
 */
finishDependent?: boolean;
```

价格矩阵对 `finishDependent: false` 的型号只需要一行（用哨兵价格组），
FR-8 的"价格矩阵完整性"校验也要相应放宽——否则会误报空洞。

### 4.4 换花色比价（用户要求的功能）

报价清单末尾增加一段：

```
【换一种门板花色】
  当前：Shaker White（价格组 A）        $1,358.50
  ────────────────────────────────────────────────
  Shaker Grey    （价格组 A）  同价      $1,358.50    ±$0
  Maple Glaze    （价格组 B）  贵 62%    $2,105.20    +$746.70
  Navy Shaker    （价格组 B）  贵 62%    $2,105.20    +$746.70

  说明：以上是**同一套方案**换门板后的重算价，柜体数量与排布完全不变。
       填缝条、收口板、踢脚板会跟着换色，所以也在内；塑料地脚不随花色变。
```

实现要点，每一条都有理由：

1. **逐行重算，不给总价乘系数。** 不同型号在不同价格组之间的比例不一定相同
   （价格矩阵是逐格给的，不是一个统一倍率）。乘系数得到的数字会与真正下单时
   的数字对不上——那是最坏的一种"差不多"。
2. **只换价格组，不重排。** 换花色不改变柜体选择，方案是同一个。这让客户看到
   的是**纯粹的花色差价**，而不是混进了排布变化的差额。
3. **有价格洞的花色要标出来**，不能悄悄跳过：
   「Navy Shaker：该商家的 SB36 不供应此花色，换色需调整水槽柜型号」。
   （fixtures 里那个故意留的空洞正是为了测这条。）
4. **折扣、运费、税一并重算。** 满额折扣有门槛，换花色可能跨过门槛——只算柜体
   差价会误导。

## 5. 新商家入驻时怎么建立这份清单

流程（FR-2 已有的骨架 + 本文新增的能力标签步骤）：

```
商家提供价目表（Excel / PDF / 网页）
  → 结构化导入（spec/import.ts）
  → 逐条推断 type 与 capabilities
  → 【待确认队列】推断不确定的、以及推断出来但从未见过的组合
  → 人工确认
  → 建草稿版本 → 校验（FR-8 六项 + 价格矩阵完整性）→ 发布
  → 从此这家可以出正式报价
```

**不需要**做的事：把商家的码翻译成通用码。**需要**做的事：把商家的码打上能力标签。

### 5.1 待确认队列里必须出现的几类

- 匹配不到脸型模板的型号（已实现）；
- **能力推断置信度不足**的型号（新增）；
- **高度档位与已知常见档位不同**的（如最高只到 39"）——不是错，但要让人知道，
  因为它会影响所有高层高户型的方案；
- **声明为 monolithic 但尺寸看起来像叠装件**的，或反之。

## 7. 尚未决定的问题

1. **叠装接缝损耗是多少？** 各家做法不同（有的柜体直接叠、有的加一条 1/4" 的
   过渡条）。需要在规格里声明，不能假设 0。
2. **连体 pantry 的运输限制。** 84" 的整柜可能超过普通快递尺寸限制，运费规则
   可能不同。目前 `ShippingRule` 没有按件尺寸分档的能力。
3. **能力标签的粒度。** `ModuleRole` 现在列了 8 种，够不够用要等第三家商家入驻
   才知道。宁可先少列，需要时再加——加一个枚举值比拆一个语义混乱的值容易得多。
