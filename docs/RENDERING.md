# 二维视图渲染方案（脸型模板 + 参数化拼接）

本文是 [REQUIREMENTS.md](./REQUIREMENTS.md) 第 3.3 节的技术展开，对应 FR-4 / FR-5。
附录记录了对 `rta-generic-spec/` 四份规范文档的核实结果。

---

## 1. 结论

**"标准化柜型 → 小模板库 → 按真实尺寸参数化拼接"这个方向是对的**，RTA 品类确实适合，理由在
第 2 节。但落地时有两处需要偏离最直觉的做法：

1. **不要手绘 SVG 素材，也不要用"归一化 `<symbol>` + `transform="scale()"`"**——这个做法会
   在两个地方产出错误的图（见第 4 节）。改为**声明式脸型文法 + 代码计算绝对坐标**。
2. **脸型不是 15 张图，是 15 条数据**。用一套"把柜面递归切分成行/列"的小文法描述，新增一种
   脸型是加 3 行数据，不是画一张新图。

这同时**关闭了开放问题 1（模板由谁绘制）**：不需要任何人绘制，全部由代码生成。

---

## 2. 为什么这个品类适合（对原始判断的核实）

对照 `rta-generic-spec/` 的实际数据逐条验证：

| 原始判断 | 核实结果 |
|---|---|
| 宽度是固定级差，不是连续尺寸 | ✅ 成立。编码规范明确"宽度以 **3"** 为基本步长递增（09/12/15/18…36/39/42）|
| 脸型种类很少，翻来覆去十几种 | ✅ 成立。从尺寸规范的全部柜类归纳出 **15 种脸型**，见第 3 节 |
| 侧视图截面几乎不随型号变化 | ✅ 成立。地柜统一 24" 深 × 34.5" 高（含 4.5" 踢脚），吊柜统一 12" 深，高柜 24" 深。**3-4 个截面够用** |
| 俯视图更简单 | ✅ 成立。矩形 + 转角斜切 + 盲角 L 形 + 开门弧线，**3-5 个** |
| 型号命名自带脸型信息，可规则匹配 | ⚠️ **部分成立，有一个重要例外**，见第 5 节 |
| 材质/花色不需要额外模板 | ✅ 成立。换填充色/花纹或只做文字标注即可 |

**额外发现**：`North_American_RTA_Cabinet_Construction_Guide.md` 里有两个**渲染相关**的维度，
原方案没有考虑，但它们直接影响正视图长什么样：

- **面框 vs 无框（Framed / Frameless）**：美式面框柜正面有一圈 1-1/2" 实木面框，无框柜没有。
  画出来是两种不同的图。
- **门板覆盖方式（Overlay）**：全覆盖（露 1/4" 面框）、半覆盖（露 1"-1.5"）、嵌入式
  （门与框齐平，缝 3/32"）——三种的门缝宽度和视觉差异明显。

如果按"每种脸型手绘一张 SVG"，这两个维度会让模板数量**乘 2 再乘 3 = 6 倍**（15 → 90）。
用文法描述的话，它们只是渲染时的两个参数。这是选文法而不是选素材的最强理由。

## 3. 脸型清单（从规范文档归纳）

### 3.1 核心洞察：脸型 = 柜面矩形的递归行列切分

RTA 柜子的正视图，本质上是**把一个矩形按行/列切开，每个叶子是门、抽屉面、假抽面、开放格或
盲板**。用一个极小的文法就能覆盖：

```ts
type FaceSpec = Split | Leaf;

type Split = {
  dir: "rows" | "cols";
  children: { size: number | "*"; node: FaceSpec }[];  // size 单位为英寸，"*" 表示均分剩余
};

type Leaf = {
  kind: "door" | "drawer" | "falseFront" | "open" | "blind" | "applianceOpening" | "panel";
  hinge?: "L" | "R";
};
```

对照规范文档里的真实柜型：

```ts
// B12 —— 上部 1 抽（6"）+ 下部单开门（24"）；6 + 24 = 30 = 34.5 - 4.5 踢脚 ✓
B12: { dir: "rows", children: [
  { size: 6,  node: { kind: "drawer" } },
  { size: 24, node: { kind: "door", hinge: "L" } },
]}

// B30 —— 上部 2 个独立抽屉（横向并排）+ 下部对开门
B30: { dir: "rows", children: [
  { size: 6,  node: { dir: "cols", children: [
      { size: "*", node: { kind: "drawer" } },
      { size: "*", node: { kind: "drawer" } } ]}},
  { size: 24, node: { dir: "cols", children: [
      { size: "*", node: { kind: "door", hinge: "L" } },
      { size: "*", node: { kind: "door", hinge: "R" } } ]}},
]}

// 3DB24 —— 顶部浅抽 6" + 2 个深抽各 12"；6 + 12 + 12 = 30 ✓
3DB24: { dir: "rows", children: [
  { size: 6,  node: { kind: "drawer" } },
  { size: 12, node: { kind: "drawer" } },
  { size: 12, node: { kind: "drawer" } },
]}

// SB36 —— 假抽面 + 对开门
SB36: { dir: "rows", children: [
  { size: 6,  node: { kind: "falseFront" } },
  { size: 24, node: { dir: "cols", children: [
      { size: "*", node: { kind: "door", hinge: "L" } },
      { size: "*", node: { kind: "door", hinge: "R" } } ]}},
]}

// BBC36 盲角地柜 —— 靠墙侧 6" 盲板 + 可用门
BBC36: { dir: "cols", children: [
  { size: 6,   node: { kind: "blind" } },
  { size: "*", node: { dir: "rows", children: [
      { size: 6,  node: { kind: "drawer" } },
      { size: 24, node: { kind: "door", hinge: "R" } } ]}},
]}
```

**关键收益**：`2DB` / `3DB` / `4DB` / `VDB` 这四类抽屉柜，在"手绘素材"方案里是 4 张图；
在文法方案里是**同一个模板，抽屉数与各自高度是参数**。

## 4. 实现：为什么不能用"归一化 symbol + scale"

原方案提出用 SVG `<symbol viewBox="0 0 1 1">` + `<use transform="scale(w,h)">`。这个做法很直觉，
但会产出**两类错误的图**：

### 4.1 缝隙宽度会被一起缩放（这是硬伤）

门缝、门与柜体的留边是**绝对尺寸**——按 `Construction_Guide` 第二节，全覆盖门板露出面框
**1/4"**，嵌入式门四周缝隙固定 **3/32"**。它们不随柜子宽度变化。

但归一化模板里的缝隙是**比例值**：

| 柜宽 | 模板里 0.02 单位的缝 | 缩放后实际 | 应该是 |
|---|---|---|---|
| 12" | 0.02 × 12 | 0.24" | 0.25"（碰巧接近）|
| 36" | 0.02 × 36 | **0.72"** | 0.25" |

36" 柜子的门缝会画成 12" 柜子的 3 倍宽。这在正视图上是一眼可见的错误，而正视图恰恰是客户
用来判断"这个设计对不对"的主要依据。

### 4.2 非等比缩放会扭曲线宽

`transform="scale(36, 30)"` 是非等比的，SVG 的 `stroke-width` 会跟着各向异性变形——竖线变成
36 倍粗、横线 30 倍粗，同一张图里线条粗细不一致。可以用 `vector-effect="non-scaling-stroke"`
绕过，但这只解决线宽，解决不了 4.1 的缝隙问题。

### 4.3 正确做法：算绝对坐标，直接出几何

```
FaceSpec + 真实宽高 + 样式参数（overlay / framed）
        ↓  纯函数，确定性
    [{ x, y, w, h, kind, hinge }]      ← 绝对英寸坐标的矩形列表
        ↓
    SVG <rect> / <path>，stroke-width 固定
```

- 缝隙、面框宽度作为**绝对量**参与切分计算，不参与缩放。
- 依然**零依赖、纯代码拼接**，符合仓库现有风格；只是把"缩放一张图"换成"算好了再画"。
- 可测试性反而更好：切分函数的输出是一组数字，可以直接断言，不用比对图像。

**`<symbol>` / `<use>` 仍可用于真正重复且不需要按尺寸重算的元素**（如把手图标、开门弧线示意），
这类元素等比缩放没有副作用。

## 5. SKU → 脸型的规则匹配

`Nomenclature_Guide` 的编码规范让规则匹配可行。默认映射表：

| 前缀 | 脸型 | 备注 |
|---|---|---|
| `B` + 宽 | **F3 / F4 / F5** | ⚠️ **依赖宽度**，见下 |
| `2DB` / `3DB` / `4DB` | F6（N = 2/3/4）| |
| `SB` | F7 | |
| `FSB` / `APR` | F8 | |
| `LSB` | F9 | |
| `BBC` | F10 | |
| `BPO` / `TDC` / `BWB` | F1（外观是单门/单面板）| 内部结构不影响正视图 |
| `W` + 宽 ≤ 21 | F1 | |
| `W` + 宽 ≥ 24 | F2 | |
| `CW` / `WDC` | F9 | |
| `EWC` / `LWC` | F9 变体（L 形折叠门）| |
| `WBC` / `WBBC` | F10 | |
| `MW` / `WOC` | F11 | |
| `WWR` | F12 | |
| `PC` / `U` | F13 | |
| `OC` / `BOC` / `MIC` / `MOC` | F14 | |
| `VB` / `V` | F5 / F7 变体 | 浴室柜，按是否带盆孔 |
| `VDB` | F6 | |
| `WF`/`BF`/`TF`/`BEP`/`WEP`/`REP`/`TK`/`CM`/`SCM`/`LRM`/`BM`/`OCM` | F15 | |

### ⚠️ 重要例外：前缀不足以决定脸型，必须带宽度

`B12` 和 `B30` 前缀相同，脸型不同：

- `B09`~`B21` → 一抽一门（F3）
- `B24`、`B27` → 一抽双门（F4）
- `B30`~`B36` → 双抽双门（F5）

所以规则的键是 **(前缀, 宽度)**，不是前缀。

**而且宽度分界点是公司自定的**——有的厂把 B24 做成单门，有的做双门。因此：

> 规则表必须**可按公司覆盖**。通用表只作默认值；使用自有命名体系的公司，规则命中率会接近 0，
> 必须走 FR-2 的对话确认或模板导入。

这条直接影响 FR-2 的验收指标"脸型模板规则命中率 ≥ 70%"——该指标只在公司使用行业惯用命名时
才有意义，已记入 [PRE_LAUNCH_CHECKLIST.md](./PRE_LAUNCH_CHECKLIST.md) D4。

## 6. 规范文档没有提供、但渲染需要的信息

以下几项 `rta-generic-spec/` 没给（或只给了近似值），必须在 FR-2 录入时补，或用平台默认值：

| 缺口 | 影响 | 处理 |
|---|---|---|
| 各脸型的分格高度（抽屉 6"、门 24" 等标注为"约"）| 正视图分格位置 | 平台给默认值，公司可覆盖 |
| 门缝/留边的具体尺寸 | 见 4.1，直接影响观感 | 由 overlay 方式推导（全覆盖 1/4"、嵌入 3/32"）|
| 铰链方向（L/R）| 单门柜画在哪边、俯视图开门弧方向 | 编码规范提到是 SKU 后缀，FR-2 需捕获 |
| 面框宽度（1-1/2"）是否体现在正视图 | 面框柜与无框柜观感差异 | 按公司的 framed/frameless 属性 |
| 把手样式与位置 | 观感 | MVP 阶段统一用示意把手或省略 |

## 7. 落地建议

- **MVP-2**（按 REQUIREMENTS 第 9 节）实现：`FaceSpec` 文法 + 切分函数 + SVG 输出 +
  15 个默认脸型的数据定义 + 4 个俯视 + 4 个侧视。

  必测：缝隙不随柜宽变化、`"*"` 均分的余数分配、盲角可拉伸段、overlay 三种方式的留边差异。

  公司级覆盖放在 `ProductSpecVersion` 下。

### A15 🚫 需要明确隔离的内容

`Cabinet_Product_Substitution_And_Logic_Manual.md` **第二节"墙柜替代地柜"**（用 12" 深吊柜
加地脚和背部支撑框架当地柜用）：

这是**现场缺货时的应急改装做法**，不是标准设计做法，涉及台面承重传导与产品保修风险
（文档自己也写了"严禁悬空台面超过 2""）。

**建议**：明确标注该章节**不参与自动排布、不进入 `GenericCatalog`、不向客户展示**，仅作运营
内部参考。否则布局算法有可能生成"用吊柜当地柜"的方案——那是产品事故，不是聪明的省钱方案。

### A16 🚫 文档本身的技术缺陷

四份文档里多处 LaTeX 标记损坏：`$	imes$`（应为 `\times`）、`$\le \mathbf{0.05 	ext{ ppm}}$`
（应为 `\text`）——源文件中的反斜杠被替换成了制表符。

这些文档会被喂进 FR-2 的抽取管线，损坏的标记会污染抽取结果（例如把 `24 	imes 34.5` 读成

## 8. 统一绘图内核（v0.6 审查发现，**M5-7 / M5-8 已实现**）

> 触发：客户问「全局布局图纸跟后面各向的图纸，是用的不同的工具吗？后面的图纸
> 用的是什么开源软件？为什么前面不能用？」

### 8.1 先回答：没有用任何开源绘图软件

**全部图纸都是本项目自己拼字符串生成的 SVG**，没有 D3、没有 SVG.js、没有 CAD 内核。
理由见第 4 节：这个品类的图形是**离散尺寸的矩形拼接**，画出来只需要绝对坐标运算；
引入一个通用绘图库反而会把"缝隙宽度被缩放"这类问题带回来。这个判断不变。

### 8.2 但它们确实是两套代码——这是问题

| | `render/views.ts` | `render/plan-view.ts` |
|---|---|---|
| 画什么 | 单段墙的正视图 / 俯视图 / 侧视图 | 整套厨房拼成一张平面 |
| 坐标映射 | 自己一套 | 自己另一套 |
| 转义函数 `esc` | 自己一份 | 自己另一份（复制的） |
| 尺寸标注 | 有尺寸链 | 只有一行墙长 |
| 开门方向弧线 | 有 | **无** |
| 家电/水槽文字 | **无** | **无** |
| 配色 | 一套 | 另一套（相近但不相同） |

结果就是客户观察到的现象：两组图**看起来像两个软件画的**。它们确实"用了同一种技术"，
但没有共用同一套**绘图约定**——而客户看的是约定，不是技术。

### 8.3 做法：抽出一层绘图内核

```
render/
  kernel/
    canvas.ts      画布与坐标映射（英寸 → px），唯一的一份
    primitives.ts  rect / line / text / arc / dimension / hatch
    legend.ts      图例（从实际画出的元素生成，不写死）
    palette.ts     配色与线宽，唯一的一份
    annotate.ts    家电 / 水槽 / 填缝条的标注规则（见 APPLIANCES.md §4）
  views.ts         单墙四视图  ─┐
  plan-view.ts     全局俯视图  ─┴─ 都只负责"摆什么"，不负责"怎么画"
```

判定标准很直接：**同一个东西（比如填缝条）在两组图里必须是同一个颜色、同一种
剖面线、同一种标注方式。** 做不到这一点，客户就会觉得是两个软件。

**实现记录（M5-7 / M5-8）**：`test/render-kernel.test.ts` 把上面这条判定标准写成了
可执行的断言——填缝条的颜色、家电位的虚线、开门弧线、逐柜尺寸、水槽标注，
每一条都在两组图上各查一遍。另外三件事是写的时候才发现的：

1. **"这是什么东西"也只能有一份判断。** 光统一颜色表不够：一边把水槽柜当普通
   柜体、另一边不当，图上照样不一致。所以 `elementKindOf(placement)` 是唯一入口，
   两个渲染器都从它问。
2. **图例要先腾地方再画。** 图例画在图上方，如果只是"画上去"而不把它的高度
   加进画布，它会压在第一排柜子上。腾地方与画东西是同一件事的两半。
3. **开门弧线要算进图纸边界。** 24" 深的地柜配 0.85 倍门宽的弧线要伸出去 45"，
   而原来只按柜体进深留了 26" ——弧线被裁掉半圈，而弧线正是它的用处所在。
   同理，正视图左侧的「台面 36"」竖向标注也被裁过，所以左边距要单独算。

### 8.4 全局俯视图缺的具体内容

除了统一样式，全局俯视图还缺三样单墙俯视图已经有的东西（**均已补上**）：

1. **开门方向弧线**——客户判断"冰箱门开了会不会打到抽屉"靠的就是这个；
2. **尺寸链**——原来只标了墙总长，没有逐柜宽度；
3. **家电与水槽标注**——见 `APPLIANCES.md` §4，这是硬性要求。

反过来，单墙俯视图也补上了它缺而全局俯视图有的那样：**墙上的特征**
（窗/上下水/燃气口）。同一面墙在两张图上一张标了窗一张没标，客户会怀疑
哪张是错的。

### 8.5 叠装吊柜的横向接缝

`CATALOG_MODEL.md` §3 引入叠装后，正视图上会出现**横向接缝**。它必须画出来：
客户看到的成品上那是一条实实在在的线，图上没有就是图画错了。

同一面墙上的横缝高度应当一致（软约束，见 `CATALOG_MODEL.md` §3.2），
不一致时正视图会呈现锯齿——所以这条约束也要**在正视图上可验证**。

### 8.6 全局俯视图必须是**一张连通的平面**（v0.9，M5-14～M5-19 已实现）

客户的第二段话：「全局视图要把几个墙围起来、连起来，不能像四个单独的视图那样，
把南墙、北墙、东墙分开写。只有把它们连起来的时候，才会发现开关门的问题、
干涉的问题，以及一些边角柜等细节。」

#### 8.6.1 为什么原来连不起来

不是画法问题，是**数据默认值**问题。手工/对话录入墙段走的是 `addWallRun`，
它把 `startsAtCorner` / `endsAtCorner` 默认成 `false`——于是任何手工录入的
U 型厨房，三段墙彼此不相接，`layoutPlan` 只能把它们并排画开并附一句
「示意排列」。从图里识别的那条路径本来就按"首尾相接"推，两条路径的默认值
不一致，是"同一件事有两份判断"的又一例。

#### 8.6.2 平面模型只有一份

`src/layout/plan-model.ts`。改造前"墙段怎么串"有两份复制：`plan-view.ts` 的
`layoutPlan` 按 `startsAtCorner` 串，`generate.ts` 的 `trianglePoints`
**无条件**每段右转 90°。两份对同一个户型给出不同的平面——一份用来画图，
另一份用来算工作三角，而没有任何地方会报错。

现在墙角归属、围合区、岛台落位、构件世界坐标足迹全部从这一份出。

#### 8.6.3 图上新增的三样东西

1. **墙角界线 + 转角柜**——让位那一侧画一条虚线加「转角」字样，说明这段墙的
   柜子为什么不是从墙角起排的。让出来的地方**不画方块**：那块地方被相邻墙段的
   柜子占着，图上本来就看得见，再盖一个方块只会把它挡住。
2. **台面外沿**——台面比柜体箱体大出一圈（前沿与外露端头各 1-1/2"）。
   门洞旁"要让出一点点距离"的那一点，就在这一圈上。俯视图里台面只画轮廓
   不填色，填了会把柜体和水槽盆全盖住。
3. **过道尺寸**——岛台到四周柜列的净空，标成尺寸链。口径与 `checkAisles`
   完全一致（都量台面外沿之间），图上标 42" 检查里判 42"，客户拿尺子量图也是 42"。
