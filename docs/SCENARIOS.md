# 场景走查（配套 REQUIREMENTS.md v0.4）

本文件是 [REQUIREMENTS.md](./REQUIREMENTS.md) 第 4 节的详细展开，按"角色/租户"分组，覆盖
消费者账号、专业（贸易）账号、供给侧公司、平台运营四类参与方的完整端到端旅程。每个场景标注
对应的 FR。

> **v0.4 变更**：场景 A 第 6 点的矛盾已修正（未订阅公司**可以**被 `@`，拿到 `EstimateDraft`）；
> 场景 A 增加门板/价格组录入与验收；场景 C 改为确定性 `@` 路由；场景 D 增加修订链；
> 场景 E 增加税费/有效期、服务端闸门、发送前披露、计费去重与争议；场景 H 增加去标识化硬规则；
> 新增场景 I（公司发现与招商引流）。

## 场景 A：公司入驻（供给侧租户视角）

对应 FR-2 | 角色：公司运营/店长

1. 运营/店长进入自己公司专属的**后台入驻会话**（与客户端对话框是完全分开的入口），此时该公司
   在系统里的状态是 `CabinetCompany.status = onboarding`。
2. 上传现成资料——产品手册、价格表、规格书，PDF/图片/Excel 都行，格式不要求规整。
3. 系统在会话里持续追问，补全资料里模糊或缺失的信息：
   - **柜体型号**：型号码、类型、每种类型的标准尺寸档位；
   - **门板样式与价格组**：这家公司有哪几档门板（如 Shaker White / Maple Glaze），
     每档属于哪个价格组——**这是定价的主维度**（见 REQUIREMENTS 3.5）；
   - **(型号 × 价格组) 价格矩阵**：同一个 B12 在不同价格组是不同的价，矩阵允许有空洞
     （某型号不供应某价格组）；
   - **五金/配件选项**及加价规则、**折扣规则**（含贸易折扣——如果这家公司本来就对建商/经销商
     有一套单独报价，这一步一起整理进去）、**运费规则**、**适用税区**；
   - **脸型模板归属**：系统先按型号命名规律猜（B12 / W2430 / SB36 这类命名自带信息），
     猜不出来才问人。
4. **任何抽取不确定的字段都会进"待确认队列"并标注置信度，系统不会自己猜一个值蒙混过去。**
   运营在会话里逐项确认。
5. 系统汇总成一份产品规格文档（人读版 + 结构化版），运营/店长可以直接改。
6. 确认发布之前，这份规格处于 `ProductSpecVersion.status = draft`，对客户端完全不生效——
   草稿不会被公司 Agent 拿去回答客户，也不会参与报价生成。
7. 运营/店长确认发布 → 系统生成一个**不可变**的 `ProductSpecVersion`（`status = published`，
   `versionNo` 递增）。以后要改规格，是在这一版基础上开一个新的 `draft`，而不是就地改写已发布
   的版本（见 REQUIREMENTS 3.6）。
8. **发布 ≠ 可产生 `Quote`。** 还需要完成个性化服务的订阅
   （`billingPlan.personalizationSubscription = active`）；发布 + 订阅同时满足，
   `CabinetCompany.status` 才变成 `active`。
   - **（v0.4 修正）** 只发布了规格但还没订阅时，这家公司**仍然可以被客户 `@`**，只是客户拿到
     的是场景 B 的 `EstimateDraft` 而不是绑定这家公司的 `Quote`，同时系统记一条
     `CompanyMentionSignal(resolutionStatus = matchedInactive)`。
     旧版这里写的是"不可 `@`"，与 FR-10 冲突，本版以 FR-10 为准。

### 验收（FR-2 量化标准）

试点公司的规格录入完成后，按 REQUIREMENTS.md FR-2 的验收表逐项核对：SKU 召回率 ≥ 98%、
**价格准确率 = 100%（抽样 50 条，0 容错）**、必填字段覆盖率 ≥ 95%、脸型模板规则命中率 ≥ 70%
且最终准确率 100%、静默失败数 = 0、人工修正 ≤ 30 次、端到端 ≤ 2 人时。

不达标时走**降级路径**：改用平台提供的结构化 Excel 模板导入（型号表/价格矩阵表/门板表/
选项表四张 sheet），FR-2 会话降级为"校对助手"，负责比对导入结果与原始 PDF、指出缺漏与可疑项。
MVP-1 的其余环节不因规格录入不达标而阻塞。

## 场景 B：消费者账号 —— 冷启动通用层体验（尚无相关公司入驻）

对应 FR-10 | 角色：消费者账号 | 前提：客户想了解的品类/地区暂无 `active` 状态的公司

1. 客户打开对话框，跟总控助手聊装修需求（厨房大小、风格、预算、城市/省份等），流程跟场景 C
   前半段完全一样——**客户不需要预先知道"现在有没有公司入驻"这件事，体验上是无缝的**。
   （省份是必填项之一，后续定价要用它决定税率。）
2. 客户想找具体某家公司问细节，但打的公司名不是 `active` 状态（不存在 / `prospect` /
   `onboarding` / 已发布规格但未订阅）。这句话不会得到"查无此公司"这种生硬报错，而是：
   - 系统按归一化后的名称匹配，记录一条 `CompanyMentionSignal`（带 `normalizedName` 与
     `resolutionStatus`，供后续销售外联使用）；
   - 对客户的提示语气是"这家公司暂时还不能直接对话"一类的委婉说法，**不暴露"入驻/订阅状态"
     这类内部运营细节**；
   - 总控助手继续用通用知识回答客户当下的问题，不中断对话。
3. 客户可以直接让总控助手基于已收集的需求出一版**通用预估**——系统用平台共享的 `GenericCatalog`
   （行业典型尺寸与报价区间，不属于任何具体公司）生成一份 `EstimateDraft`，明确标注"行业典型
   区间，非具体公司真实报价"，给的是价格区间不是精确数字。
4. MVP-1 阶段这份预估是纯文本形式（户型图上传/四视图渲染依赖 MVP-2 的能力）；MVP-2 之后会升级
   成带四视图示意的版本，复用跟 `Quote` 一样的脸型模板渲染逻辑，只是数据来源换成
   `GenericCatalog`。
5. `EstimateDraft` **没有 `companyId`，天然没有收件地址**——它不会、也不可能被推进到发送闸门
   （FR-8）。客户在这个场景里能拿到的最终产物就是一份预估，不会误发给任何公司。

## 场景 C：消费者账号 —— 个性化对话与 @ 路由

对应 FR-1 | 角色：消费者账号 | 前提：至少一家相关公司 `status = active`

1. 客户默认与总控助手对话——通用向导环节，不涉及具体某家公司，一次只追问 1-2 个关键缺口
   （厨房大小、布局、风格、材质倾向、预算、工期、**所在省份**）。
2. 客户想问某家已入驻公司的具体细节，在输入框打 `@` → 弹出**公司联想选择器** → 选中"枫叶橱柜"
   → 消息体里带上结构化 mention token `{ companyId, displayName }`。
3. 服务端**只按 `companyId` 路由**，不做自然语言的公司名推断。回答只基于这家公司
   `published` 规格版本里真实存在的数据——回答不了就是回答不了，不会编，也不会借用别家公司
   的信息。
4. 如果客户是粘贴/手打的公司名（没走选择器），服务端做**确定性匹配**：规范化后与
   `CabinetCompany.name` 及 `aliases[]` 精确比对。
   - 唯一命中且 `active` → 路由；
   - 命中多个 → 总控助手回问"你是指以下哪一家？"并列出候选，**不猜**；
   - 命中 0 个或命中的公司未 `active` → 走场景 B 第 2 点的处理。
   - **LLM 不参与"这是哪家公司"的判断**——在一个以数据隔离为硬性要求的系统里，
     "客户以为 @ 的是 A、实际路由给了 B"是不可接受的故障。
5. 客户可以在一句话里同时 `@` 好几家已入驻公司，横向问同一个问题，各家分别独立作答。

## 场景 D：消费者账号 —— 户型图上传 → 四视图 → 修改

对应 FR-3、FR-4、FR-5 | 角色：消费者账号 | 前提：已 `@` 至少一家 `active` 公司

1. 客户上传一张户型图片（暂时只支持图片；如果客户手上是 CAD 图纸，引导截图当图片处理；如果
   是从别家/专业设计软件拿到的报价单或方案截图，也走同一条上传入口，见 FR-3）。
2. 系统用图像理解/OCR 估算房间轮廓和关键尺寸。精度上 1/4 英寸颗粒度就够，但**完整性优先于
   精度**：拿不准的地方进 `FloorPlan.unresolvedItems`，系统主动在对话里跟客户核对，或者要求
   客户手动补一个具体数字，不会因为"猜不准"就悄悄跳过某一段墙。
3. 客户已经 `@` 的这家公司之下，系统**全自动**生成一版初步方案——贴着墙面，只用这家公司
   **当前 `published` 规格版本**里真实存在的型号与离散尺寸去排布。
4. 客户没有拖拽编辑器，只能通过对话提修改意见（"这段太窄了换成 30 寸的""水槽下面要留个抽
   屉"），系统重新计算受影响的那部分，不是每次全部推倒重来。
   - **每次修改生成一个新的 `DesignRevision`（`revisionNo` 递增），不覆盖上一版**——
     "只重算受影响部分"说的是计算过程，不代表可以就地改写历史（见 REQUIREMENTS 3.6）。
5. 产出四张图：正视图、俯视图-地柜层、俯视图-顶柜层、侧视图，用脸型模板库参数化拼接生成（不是
   AI 画出来的，是按真实计算出的位置数字拼出来的）。
6. 客户在这个环节还要选定**门板样式**——它决定整单落在哪个价格组，直接影响报价（见场景 E）。

## 场景 E：消费者账号 —— 多公司比价与报价确认发送

对应 FR-6、FR-7、FR-8、FR-13 | 角色：消费者账号 | 前提：已对至少一家公司走完场景 D

1. 客户可以对好几家 `active` 公司分别走一遍场景 D，得到各自的方案和报价。
2. 这几家之间**只做价格层面的横向对比**（一张表列出每家总价和主要差异项），不做图纸/视图并排
   对比。对比表会标注各家的**含税口径**是否一致，避免拿含税价和未税价直接比。
3. 报价单由 `PricingEngine` 生成，逐行给出：型号码、数量、尺寸、门板样式与价格组、五金/配件、
   单位标价、折扣后单价、行小计；单据层给出小计、折扣明细、**运费**、**分项税（税种 + 税率 +
   金额）**、总价、币种、**有效期 `validUntil`**。
   - **价格全部由代码算，LLM 不参与。** 模型只负责产出"选了哪些型号、什么尺寸、什么门板、
     什么五金"这组选择，任何模型输出里的金额字段都会被丢弃（FR-8 第 1 条）。
4. 生成 `Quote` 之前，系统跑完 FR-8 的 6 项硬校验：型号存在于该公司 `published` 版本、
   尺寸在离散候选集内、门板对应的价格组在价格矩阵里对该型号有条目、五金/配件适用、
   省份税率可查、引擎重算与快照逐项一致。
   - 任一项失败 → **直接拒绝**，记 `QuoteAuditEvent(validationRejected)`，不做"自动修正后
     继续"，也不进入发送闸门。
5. 客户对某一家的设计和报价明确表示"我确认了"：
   - 这是一次**服务端状态变更**（`Quote.status: draft → confirmed`），留痕写
     `QuoteAuditEvent(confirmed)`；
   - **不是**在请求体里带一个 `confirm: true` 字段就算数（旧版做法等于把闸门交给调用方，
     任何能访问接口的人都能绕过，见 FR-8 第 3 条）。
6. **发送前的二次披露（FR-13）**：界面逐项列出"将要发送给 XX 公司的内容"——四视图、尺寸、
   需求摘要、你的联系方式，并说明该公司会因此获得联系你的能力。客户看到这个清单后才点发送。
7. 客户确认发送后，系统给这家公司登记的报价邮箱发一封 HTML 邮件：四视图拼图直接嵌在正文里，
   价格明细也是嵌在正文里的表格；同时带纯文本兜底版本、图片文件附件兜底。
   没配置真实发信账号时，这一步是预览模式，不会真的发出任何邮件（这是**第二道**闸门，不是
   唯一一道）。
8. 发送成功后：
   - `Quote.status → sent`，写 `QuoteAuditEvent(sent)`（含内容哈希）；
   - **计费按去重规则处理**：同一 `(companyId, conversationId)` 在 30 天窗口内只产生**一条**
     `LeadBillingEvent`。窗口内的重复发送照常发邮件（客户改了设计再发一次是正常行为），
     但只记 `QuoteAuditEvent(suppressedDuplicateBilling)`，不重复计费。
   - 公司在发送后 **14 天内**可对该条线索提起争议（重复/无效联系方式/超出服务范围/垃圾线索）；
     争议期内该笔费用不进入 `invoiced`，由平台运营依据审计事件与投递回执裁定
     （维持 / 全额退 / 部分退），见 REQUIREMENTS 8.1。
9. 报价超过 `validUntil` 未被处理 → `status → expired`，需重新生成（价格可能已随规格新版本
   变化）。历史报价的金额不会因为公司改价而漂移——`Quote` 冻结了 `specVersionId` 与逐项价格
   快照（REQUIREMENTS 3.6）。

## 场景 F：贸易/建商账号 —— 多项目管理

对应 FR-9、FR-11 | 角色：`trade` 账号

1. 建商/装修公司注册的是 `trade` 账号（区别于默认的 `consumer` 账号），付费订阅生效
   （`subscriptionStatus = active`）。
2. 跟普通消费者不同，`trade` 账号一个月可能要接好几单项目，每单都要单独比价——账号下能同时
   管理**多个 `Conversation`**（多项目并行），而不是像消费者那样一个账号基本对应一个进行中的
   装修项目。
3. 场景 B/C/D/E 的流程本身对 `trade` 账号完全适用（同一套底层引擎），差异只在账号层面多了
   "项目列表/切换"这一层，以及下面场景 G 的定价可见性差异。
4. 对话交互上，`trade` 账号是更"直给"的模式——建商懂行业术语，不需要新手教育式的引导提问：
   每轮可以一次问全（消费者是 1-2 个字段）、不解释基础术语、不反复确认已说过的信息。
   **差异只在"问法"上，不在能力上**——报价、校验、发送闸门一律与消费者相同。
   让专业账号绕过闸门会直接破坏 FR-8，所以交互模式里不存在任何"跳过校验"的开关。
5. 项目列表给出每个项目的状态（收集需求 / 已出方案 / 已报价 / 已发送 / 沉寂）、涉及公司数、
   最低报价，以及**超过 30 天没动静的项目**——建商手上单子多，需要知道哪几单卡住了。
6. `trade` 账号需要**资质核实**（营业执照 / GST 号），见场景 G 第 1 点。

## 场景 G：贸易/建商账号 —— 贸易价可见性

对应 FR-11 | 角色：`trade` 账号 + 已入驻公司

0. **前置门槛（v0.5 定案，原开放问题 7）**：拿到贸易价需要**两道门槛都通过**——
   人工资质核实（提交营业执照 / GST 号 + 注册名，运营 2 个工作日内审核）**且**订阅有效
   （`active` 或 `trial`）。任一不满足，该账号按 `consumer` 定价。

   关键在于这个门槛落在**定价链路**上而不是界面上：报价生成时用的是
   `effectiveAccountType()` 而不是 `account.accountType`，所以绕过界面直接打 API
   也拿不到贸易价。降级时响应里如实说明原因与下一步，不静默按零售价出单。

   只存证件**编号**，不存证件影像——核实只需要一个可查证的号码（FR-13 最小化原则）。

1. 门槛通过后，建商在场景 D/E 生成报价单时，`PricingEngine` 按 `accountType = trade`
   自动应用贸易定价，两种表达方式都支持（取决于这家公司自己怎么定的，见 REQUIREMENTS 3.5）：
   - `DiscountRule(audience: trade)`——标价的 X% off，可按订单金额分档，可只对部分价格组生效
     （这是行业里更常见的做法）；
   - `PriceMatrixEntry.tradePrice`——少数公司确实维护两张独立的价格矩阵。
2. 所用的折扣规则会记进 `Quote` 快照（`appliedDiscountRuleIds`），报价单上逐项显示折扣明细，
   建商能看清每一分钱是怎么来的。
3. 这个价格差异的现实背景是：建商拿到贸易价后，通常会自己加价再报给自己的客户（业主）——系统
   只负责如实反映"这家公司给这个账号类型的真实价格"，不涉及建商自己怎么加价（那是建商自己的
   商业行为，不在本系统范围内）。
4. 计费逻辑不变：无论是消费者账号还是 `trade` 账号触发的确认发送，都照常（按去重规则）生成
   `LeadBillingEvent` 计给对应公司；`trade` 账号自己的订阅费是独立的第三条收入线，
   见 REQUIREMENTS 第 8 节。
5. `accountTypeAtQuote` 会写进报价快照——客户从 `consumer` 升级成 `trade` 之后，
   历史报价单的价格不会跟着变。注意快照里记的是**生效**类型：资质审核期间出的报价
   记的是 `consumer`，这与当时实际算出来的价格一致，事后对账不会错位。

## 场景 H：未入驻公司的销售信号

对应 FR-10、FR-13 | 角色：任意账号（消费者或专业）+ 未 `active` 的公司

1. 只要客户在对话里 `@` 了一个系统里不存在、或状态还不是 `active` 的公司名字（场景 B 第 2 点
   已经描述过客户侧体验），系统就记录一条 `CompanyMentionSignal`：
   - `rawMentionText`：客户原话；
   - `normalizedName`：**归一化后的名称**（去空格、统一大小写、去 Inc/Ltd/有限公司等后缀、
     简繁统一）——否则 "IKEA"/"宜家"/"宜家家居" 会碎成三条不同信号，销售看板没法用；
   - `resolvedCompanyId` / `resolvedProspectId`：回溯匹配到已有的 `CabinetCompany` 或市场库
     `CompanyProspect`；
   - `resolutionStatus`：`matchedActive` / `matchedInactive` / `matchedProspect` / `unknown`；
   - 谁问的（`conversationId` / `customerAccountId`）、什么时候问的。
2. 销售看板按 `normalizedName` 聚合计数——"这家公司本月被点名 7 次"比七条零散记录有用得多。
3. 这条信号的用途是给平台自己的销售/商务外联提供弹药——"已经有真实客户点名要找你们了，
   而且他手上已经拿到一版通用预估了，现在入驻能直接接住这条需求"，这比冷启动阶段空口谈
   "入驻能带来线索"有说服力得多（见 REQUIREMENTS 第 8 节）。
4. **去标识化硬规则（FR-13 第 3 条）**：外联时**不得向未入驻公司透露客户身份或联系方式**。
   话术只能用聚合/去标识信息（"近期有客户在平台上点名寻找贵司"），不得包含姓名、邮箱、电话、
   具体地址。要把真实客户线索交给这家公司，必须走正常的 `Quote` 发送闸门——也就是客户自己
   确认发送。
5. 外联渠道要走场景 I 的合法路径（公司官网表单 / 社媒 / 已订阅邮件列表），**不能**直接给
   市场库里抓来的邮箱发冷邮件。
6. MVP 阶段假设外联是纯人工跟进（运营/销售人力主导），是否配套自动化提醒/看板工具见
   REQUIREMENTS 第 12 节开放问题 8。

## 场景 I：公司发现与招商引流（平台运营视角）（v0.4 新增）

对应 FR-12 | 角色：平台运营/管理员 | 详细讨论见 [COMPANY_DISCOVERY.md](./COMPANY_DISCOVERY.md)

1. **建立市场库**：运营在管理员后台**手动触发**一次公司检索抓取（不是定时自动跑），
   系统按公开信息整理出候选橱柜公司的名称、网址、公开业务邮箱、城市/省份，写入
   `CompanyProspect`（平面文件 `data/companies.json`，MVP 阶段商家量不大，不引入数据库）。
   - 按 email 去重：已存在则更新 `lastUpdated`、保留原 `importedAt`；新的才建条目。
   - 运营可以在后台手工**增/改/删**（删是归档 `status = archived`，保留历史，因为
     `CompanyMentionSignal` 的回溯还要用它）。
2. **市场库的三个用途**：
   - 社媒广告的受众定向与地域投放决策（哪些城市没有 `active` 公司 → 重点投放）；
   - `CompanyMentionSignal` 的回溯匹配数据源（场景 H 第 1 点）；
   - 市场情报（玩家数量、地域分布、覆盖缺口）。
3. **明确不做的事**：不向市场库里抓来的邮箱发送任何形式的冷邮件群发。爬取到的邮箱**只是
   识别与匹配用的标识**，不是可投递的营销名单。
4. **合法获客路径**：
   - 平台在 LinkedIn / Facebook 等渠道投放广告（广告本身不受 CASL 的商业电子消息条款约束）；
   - 企业**主动**点击 → 访问平台落地页 → **主动勾选同意**后注册邮件列表 →
     写入 `EmailSubscription`（记录同意时间、渠道、条款版本、UA、脱敏 IP）；
   - 此后平台才可以向该邮箱发送招商邀约与产品更新邮件（`InviteEmail` / `MailingEmail`）。
   - 每封邮件必须带可用的退订链接；退订请求 **10 个工作日内**生效（CASL 要求）。
5. **另一条合法的首次接触方式**：通过公司官网的"联系我们"表单发起商务洽谈——那是对方自己
   提供的接触渠道。展会、行业协会名录同理。
6. **转化到入驻**：企业表达兴趣后，运营为其开通后台入驻会话入口，`CabinetCompany.status`
   从 `prospect` 变为 `onboarding`，进入场景 A。
7. **闭环**：企业注册邮件列表时填的公司名，与 `CompanyProspect` 做匹配；命中则把该条目的
   `status` 更新为 `subscribed`，运营能看到"投放 → 订阅 → 入驻"的转化漏斗。

## 场景 J：家电驱动的排布（v0.7 新增，**已实现**）

> 落在模拟器的**场景 H**（`scripts/scenarios.mts`）：冰箱 33"、灶台 30"、
> 烟机、洗碗机四件给了尺寸，烤箱选「不确定」→ 推定 30" 并标 `provenance: "assumed"`。
>
> 这个场景一跑就抓出一个真问题（正是第 3 条与第 8 条要防的）：推定值写进了
> 图纸说明，**却没写进报价单**——而报价单才是客户拿去下单的那一份。SR-D1
> 因此把整份报价拦在交付口。修法见 `server.ts` 的报价清单文字拼接：
> 接的是 `provenanceNote`，与图纸说明同一句措辞，不各写一版。

对应 FR-3.2、FR-4.6、FR-5.2 | 角色：消费者账号 | 前提：已上传户型图

1. 系统在选择题里问：**厨房里会有哪些家电**（多选）、**各自宽度**（给常见档位 +
   「我去量一下」+ 自填）、**想放在哪**（靠近入口 / 靠近水槽 / 你帮我定）。
   每个选项都说清它影响什么——尺寸影响留空，位置影响落台面。
2. 客户说「冰箱 33"、灶台 30"、有抽油烟机、有洗碗机，冰箱想靠近入口」。
   → 留空按 `33 + 2×1"（通风）= 35"` 而不是写死的 36"。
3. 客户对烤箱选了「我不确定」→ 走常见默认值，但记为 `provenance: "assumed"`，
   **图纸解释里如实写「烤箱位按 30" 推定，你的烤箱更宽的话这一版要调整」**。
4. 排布：**家电位置在分层之前统一确定**；抽油烟机在吊柜层让位，位置由地柜层的
   灶台决定（现在两层各排各的，吊柜层不知道灶在哪——这是要修的）。
5. 配套柜按**能力标签**查（不按码前缀猜）：冰箱上柜、冰箱两侧通高收口板、
   烟机上柜、烤箱高柜、灶下柜（不能是普通三抽柜，上抽屉会顶到灶）。
6. **商家没有冰箱上柜型号** → warnings 报出「冰箱顶部会留空当」，不静默跳过，
   由客户决定接受还是换一家。
7. 出图：**每张图上水槽画出盆的轮廓 + 龙头位置并标注「水槽」，每个家电位标出
   种类与宽度**（`冰箱 33"`）。标签放不下就用编号 + 图例，不省略。
8. 若推定值导致硬约束否决（如灶台落台区不足），提示里**必须说明它是推定的**——
   否则客户会以为自己的厨房真的排不下。

**要覆盖的边界**：全部尺寸已知 / 全部「不确定」/ 36" 冰箱塞进 90" 墙（否决）/
商家缺配套型号 / 有烟机 / 有独立烤箱 / 嵌入式灶台。

## 场景 K：商家规格差异（v0.7 新增，**已实现**）

> 核心断言落在 `test/third-company.test.ts`（Birchline：分体 pantry、39" 吊柜上限），
> 模拟器的**场景 F**跑 120" 层高 + @ 点名第三家这条链路。

对应 FR-2.2、FR-4.7 | 角色：供给侧 + 消费者 | 前提：至少两家规格设计不同的商家

1. **A 商家**：pantry 是**连体**的 `PANTRY1884`（一个 SKU、一扇通高门、
   `monolithic: true`）；吊柜最高 42"。
2. **B 商家**：pantry 是**分体**的 `PC1842` × 2（叠装，中间一条看得见的横缝、
   外加连接件）；吊柜最高 39"。
3. 同一个客户、同一个户型（层高 108"）向两家询价：
   - A 家：吊柜可用 ~48" → 42" 单柜 + 6" 加高顶线；pantry 一个 SKU；
   - B 家：39" + 一段叠装，**或** 39" 单柜 + 更高顶线。
     解不出精确匹配时**如实说明**，不能静默把 48" 变成 42"。
4. 两份报价**件数不同、行数不同、外观不同**——这是正确的结果，不是 bug。
   比价表要标明这一点，不能让客户以为是同一份东西的两个价。
5. 正视图上，B 家的叠装柜**必须画出横向接缝**；同一面墙的横缝高度要一致
   （不一致时正视图呈锯齿，属于软约束扣分项）。
6. 全程**没有任何"通用型号码"参与**：两家各自用自己的码定价、出图；
   排布器问的是同一个能力问题（「18" 宽、84" 高的储物高柜」），两家各自回答。

**要覆盖的边界**：连体 vs 分体 / 42" vs 39" 档位 / 层高 96"（不用拼）、
108"（可拼可不拼）、120"（一定要拼）/ 叠装解不出来时的降级说明。

## 场景 L：换花色比价（v0.7 新增，**已实现**）

> 实现在 `src/quote/finish-comparison.ts`，接在 `/api/quotes` 的响应与报价清单
> 文字末尾。断言在 `test/finish-comparison.test.ts`。
>
> **价格空洞那一支只有单元测试，没进模拟器场景集**：造一个真空洞要从试点公司的
> 价格矩阵里挖掉一行，而那一行正被别的场景用着——挖了它，别的场景验的就不是
> 原本要验的东西了。单元测试里挖的是一份拷贝，影响范围到此为止。

对应 FR-6.3、§3.5.5 | 角色：消费者账号 | 前提：已出报价清单

1. 报价清单末尾列出**同一套方案**换其他门板花色的重算价，逐行重算
   （不是给总价乘一个系数——价格矩阵是逐格给的，倍率不统一）。
2. 只换价格组、**不重排**，让客户看到纯粹的花色差价。
3. 填缝条、收口板、踢脚板**跟着换色**（这正是它们存在的理由）；
   **塑料地脚不换**——它藏在踢脚板后面，没人看得见。
4. 某花色在某型号上有**价格空洞**（商家不供应该组合）时**标出来**：
   「Navy Shaker：该商家的 SB36 不供应此花色，换色需调整水槽柜型号」，
   不悄悄跳过。
5. 折扣、运费、税**一并重算**——满额折扣有门槛，换花色可能跨过门槛。

**要覆盖的边界**：同价格组换色（差额 0）/ 跨价格组 / 有价格空洞 /
换色后跨过满额折扣门槛。

## 场景 M：连通的平面 —— 墙角、门洞、岛台（v0.9 新增，**已实现**）

对应 FR-4.3.1 ~ FR-4.3.4、FR-14 | 角色：消费者账号 | 前提：走到 `planReview`

客户看过第一版图纸后的原话：「全局视图要把几个墙围起来、连起来，不能像四个单独
的视图那样，把南墙、北墙、东墙分开写。只有把它们连起来的时候，才会发现开关门的
问题、干涉的问题，以及一些边角柜等细节。」

1. 客户口述「U 型，三面墙都是 11 尺」，一段一段录进来。三段墙**默认首尾相接**——
   报的是一圈连着的墙，不是三面各自孤立的墙。全局俯视图上它们围成一个 U，
   不再是三条并排的横条加一句「示意排列」。
2. 两个内墙角各归**长的那一段**（等长时归链上靠前的），转角柜排在它上面；
   另一段让开「相邻段进深 + 3" 转角填缝条」= 地柜 27"、吊柜 15"。
   图上让位处画一条虚线加「转角」字样，说明这段墙的柜子为什么不是从墙角起排。
3. 交付前审核跑 `INTERFERENCE`：把每个构件放进世界坐标两两比足迹。
   两段墙的柜子占同一块地方 → **阻断**。这一项是 `GEOMETRY` 的盲区：
   那两个柜子不在同一段墙上，各自都"没超墙"。
4. 门洞旁的柜子退开「台面端头外伸 1-1/2" + 门套线」。图上画出**台面外沿**——
   让出来的那一点距离，客户要看得见，否则它看起来像一条没道理的缝。
5. 客户说「中间想加个岛台，做七尺」。岛台落在围合区中央，与每一面墙的过道
   都标成尺寸。过道 <36" **阻断**（人过不去），<42" 提示（弯腰开柜门会顶到对面）。
   量的是台面外沿之间，与检查器同一个口径——客户拿尺子量图，量到的就是图上写的数。
6. 岛台**不生成吊柜层**：它头顶上没有墙。

**要覆盖的边界**：一字型（无墙角）/ L 型（一个墙角、两条边敞开）/ U 型（两个墙角、
中间段两头都让位）/ 墙段拼不上时的「示意排列」降级 / 岛台放得下与放不下 /
门洞紧贴墙角。

**这一组同时暴露的一件事**：场景 B、C 原来的墙长是在"墙角还不存在"的时候写的，
把让位算进去之后，它们编码的是**物理上不成立的厨房**（U 型 108" 的中间墙只剩
54" 可用，摆不下水槽 + 两侧工作台面）。场景已按能成立的尺寸更正——
这不是把测试改绿，是把测试夹具改成真实存在的厨房。

# 供给侧与平台侧场景（v1.0 新增）

前面的场景绝大多数是**需求侧**：客户怎么问、怎么看图、怎么拿到报价。
但这个平台有三方——客户、商家、平台运营——而后两方此前只有场景 A 和场景 I
两条，且都停在"设计写了"的阶段。

这一组补的是**商家和平台运营真正会做的那些事**，判据是同一条：
每个场景都要能指出一个「不这么做会怎样」的具体后果，而不是"把功能列一遍"。

## 场景 N：商家自助录入并发布规格（v1.0 新增，**已实现**）

对应 FR-2、场景 A | 角色：商家运营/店长 | 前提：平台已为该公司开了后台入口

1. 商家先拿**空白模板**（`GET /spec/templates`）：四张必填表 + 一张可选的箱体板材表。
   让商家猜我们要什么格式，等于让他猜错三次。
2. 开一段录入会话（`POST /spec/sessions`），同时产生一个 `draft` 版本。
   **已有没发布的草稿就接着那一段**——每次点"开始录入"都开一段新的，商家会攒下
   一堆半截会话，而且分不清哪一段是他昨天填到一半的那个。
3. 导入模板。回包里**同时给"进来几条"和"卡住几条"**：只报一句"导入成功"，
   商家不会知道他 200 个型号里有 30 个根本没进来。
4. 卡住的逐条进**待确认队列**并变成一句人话的追问。系统会给候选建议，
   但**从不自动采用**——这是 FR-2「零静默失败」的落点。
5. 队列没清空**不允许发布**，且要说清楚拦的是哪一条。「发布失败」对商家毫无用处。
6. 发布产生**不可变**的 `ProductSpecVersion`，原 published 转 archived。
7. **发布 ≠ 能出报价**：还要订阅生效。不说这一句，商家会以为自己已经上线了，
   然后奇怪为什么一条线索都没有。

**要覆盖的边界**：干净的表一次过 / 脏表反复导 / 队列没清空就想发布 /
只给必填表不给箱体表 / 重复开会话。

## 场景 O：脏价目表（v1.0 新增，**已实现**）

对应 FR-2 零静默失败 | 角色：商家运营

真实商家给的第一版表**一定是脏的**。这个场景把常见的脏法一次全塞进去：

1. 型号类型写成商家自己的叫法（`Base Cabinet` 而不是 `base`）→ 认不出，进队列，**不猜**；
2. 门板引用了一个价格组表里没有的组代码 → 整行不进，进队列；
3. 型号命名不符合任何规律（`X-9981`）→ 脸型判不出，进队列；
4. 价格写成 `$1,245.50 CAD` → 能洗的洗掉（`$`、逗号、空格），洗不动的进队列；
5. 备注里带英寸符号 `1/2"` → **不能炸掉整张表**（RFC 4180：只有字段开头的引号才是引号）；
6. 有型号在价格矩阵里一行价都没有 → 发布时拦下并点名是哪几个。

**判据不是"能导进来多少"，是"没进来的有没有全部被报出来"。**
静默吞掉一行，商家的客户就会拿到一份少了那个型号的方案，而没有人会发现。

## 场景 P：改价与版本（v1.0 新增，**已实现**）

对应 §3.6 | 角色：商家运营

1. 商家已发布 v1，客户拿到了一份报价。
2. 商家涨价，开新草稿 → 导入新价目表 → 发布 v2。v1 自动转 `archived`。
3. **已发出的那份报价金额一分不变**——它冻结了自己的快照（`Quote` 的
   `specVersionId` / `taxRuleSnapshot` / `lineItems`）。
4. 新客户按 v2 报价。
5. 试图直接改已发布的 v1 → 拒绝（`IMMUTABLE_VERSION`），要求开新草稿。

**不这么做会怎样**：商家周二调价，客户周一拿到的报价单周三打开变成了另一个数——
那是纠纷，而且我们无法自证当时报的是多少。

## 场景 Q：线索计费与争议（v1.0 新增，**已实现**）

对应 FR-7、FR-8.1 | 角色：商家运营 + 平台运营

1. 客户确认发送报价 → 商家邮箱收到 → 平台记一条线索计费事件。
2. 同一个客户 30 天内再发一次同一家 → **邮件照发，但不重复计费**。
   去重键在数据层有唯一约束，不靠调用方"记得判重"。
3. 商家在自己的后台看得到每一条计费事件**和它的来由**（哪段会话、哪份报价）。
   只给一个月账总数，商家没法核对，也就没法信。
4. 商家对某一条发起争议，给理由和证据。
5. 平台运营在裁定台上看到，裁定"免单"或"维持"，**结果和理由都要落到事件上**。
6. 已裁定的事件不能再次发起争议（重复争议会让账目对不上）。

## 场景 R：商家之间的隔离（v1.0 新增，**已实现**）

对应 §5 租户隔离 | 角色：两家商家

这个场景只有一件事：**A 家用自己的令牌，去碰 B 家的每一样东西，全部要被挡住。**

- 读 B 家的计费事件 → 挡
- 改 B 家的规格草稿 → 挡（令牌证明了你是哪一家，会话必须**也**属于那一家）
- 发布到 B 家的版本链上 → 挡
- 不带令牌 → 挡
- 拿"公司不存在"和"令牌不对"作对比 → **两者返回同样的说法**，
  否则谁都能枚举出平台上有哪些公司

**不这么做会怎样**：这是一个多商家平台，互为竞争对手。一次越权读取就是
把一家的价目表交到另一家手上，而这件事不会有任何报错。

## 场景 S：平台运营的日常（v1.0 新增，部分实现）

对应 FR-12、上线闸门 | 角色：平台运营

1. **上线闸门**：哪几项还没核实、哪几项会阻断生产启动，一张表看完。
2. **招商漏斗**：`CompanyProspect` 从 `prospect` → `subscribed` → `onboarding`，
   看得到转化。
3. **销售信号**：客户 @ 了一家还没入驻的公司 → 记一条信号。看板上只给**聚合计数
   与外联话术，不含任何客户身份**（FR-13 第 3 条）。
4. **贸易资质审核**：待审列表 → 通过/驳回 → 驳回要写原因，且该账号立刻按
   consumer 定价（不是界面隐藏，是定价链路上生效）。
5. **留存到期清除**：生成清除计划。⚠️ **定时任务尚未接线**（上线阻断项 B6），
   目前只出计划不执行。
