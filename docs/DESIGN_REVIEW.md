# 设计与实现的对齐审查（v0.5 后）

> 触发：完成 MVP-1~3 与 v0.5 各项之后，检查**文档说的**与**代码做的**是否一致，
> 以及哪些地方还需要提升。方法是先跑一遍端到端模拟（`scripts/simulate.mts`，
> 三套厨房走真实 HTTP 端点），再逐条比对 FR 与实现。
>
> 结论先说：**核心链路（定价、闸门、计费、渲染、解释）是对齐的且质量不错；
> 供给侧（公司入驻、规格发布）几乎完全没有接线——文档写了完整流程，实现只有库函数。**

---

## 0. 端到端模拟暴露的问题（已修）

跑模拟比读代码有用——三个问题是读代码不会发现的：

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| 1 | 客户**没有任何入口**告诉系统窗户/上下水在哪 | 没有视觉模型时（当前默认），**每套厨房都排不出水槽柜**。模拟里 A 厨房排出 `B36×4`，一个水槽都没有 | 已修：`addFeature` 接到 `/resolve` |
| 2 | 组装偏好套到不提供该形式的柜体上 | 吊柜只提供 RTA，客户选「组装好发货」→ **整单报价被 422 拒绝**，客户只看到"报价校验未通过" | 已修：按 `assemblyOptions` 过滤 + 如实报告未落实项 |
| 3 | 助手连着三轮问同一个问题 | 客户答了「质感优先」「门板选深色」，但关键词表匹配不到「风格」，于是原样再问一遍 | 已修：识别重复提问后改口去用选择题 |

第 1 条最值得记：`addFeature` 函数**早就写好了**，有完整实现，只是**没接到任何端点**。
这类"库函数齐全、接线缺失"的问题在下面还会反复出现。

## 1. 最严重的一处：公司侧端点没有鉴权（已修）

```ts
// 修之前
app.get("/api/company/:companyId/billing", (c) => {
  const scope = new TenantScope(param(c, "companyId"));   // ← id 来自 URL
  return c.json({ events: scope.filter(appCtx.repos.billingEvents.all()) });
});
```

`TenantScope` 确实按 companyId 过滤了，但**那个 id 是调用方自己填的**。
这不是隔离，是拿攻击者可控的输入做过滤——换一个 companyId 就能读到别家的计费事件
（含客户账号 id、会话 id、报价 id、金额），还能代别家提争议。

**这正是 FR-9 与 §3.4 承诺不会发生的事。** 而且它比 E1 更严重：E1 是"登录态还不完善"，
这个是"隔离机制在设计上就不成立"。

修法：`src/tenancy/company-auth.ts` —— 每家公司一个访问令牌，`X-Company-Token`
必须与 URL 里的 companyId 对得上；运营令牌可代公司操作（客服场景）；
定长比较避免时序泄露；不存在的公司与令牌不对返回**同样的说法**，不让人枚举公司。

**这不是公司账号体系**（没有登录、多用户、权限分级、令牌轮换）——那属于 E1。
这里只是让隔离先真的成立。

教训：**租户隔离的前提是先证明你是谁，再按你的身份过滤。顺序反了，过滤只是装饰。**
写 `TenantScope` 时假设了"调用方身份已确认"，但从来没有人确认过。

## 2. 设计与实现的对齐情况

### 2.1 对齐得好的部分

| 需求 | 实现 | 说明 |
|---|---|---|
| §3.5 定价模型 | `pricing/engine.ts` | (型号×价格组) 矩阵 + 修饰项 + 折扣 + 运费 + 分省税，整数分运算。价格矩阵有洞时抛 `PRICE_MATRIX_HOLE` 而不是回退 |
| §3.6 版本化与可追溯 | `spec/version.ts`、`quote/state.ts`、`layout/store.ts` | 规格版本发布后不可变、报价价格快照、修订链只追加、审计事件带内容哈希 |
| FR-8 发送闸门 | `server.ts` + `quote/state.ts` | 状态机在服务端，请求体里的 `confirm` 无效，有测试专门盯 |
| FR-4/4.1 排布 | `layout/` | 硬约束/软约束/造价三层分开处理，硬约束不参与权衡 |
| FR-5/5.1 渲染与解释 | `render/` | 声明式脸型文法 → 绝对英寸 → SVG；解释全部来自算出来的结果 |
| FR-7 计费 | `billing/lead-events.ts` | 30 天去重（数据层唯一约束兜底）、14 天争议窗口 |
| FR-13 隐私 | `privacy/retention.ts`、`email/sender.ts` | 同意记录、发送前披露、去标识化、留存计划、数据主体权利 |
| FR-1.1 选择题 | `preferences/questions.ts` | 选项来自真实规格库，价格影响由代码算 |
| FR-1.2 模型分层 | `agents/model-tiers.ts` | 三层 + 确定性升级判断 |

### 2.2 文档写了、实现没接线

这是最集中的问题。**库函数都在、测试也有，但没有任何 HTTP 端点**：

| 需求 | 已实现的函数 | 缺什么 | 后果 |
|---|---|---|---|
| **FR-2 公司入驻规格录入** | `spec/import.ts` 的 `importSpecTemplates`、`blankTemplates`、入驻会话 | **零个端点** | 公司**无法通过产品流程入驻**。现在的两家试点公司是硬编码 seed。FR-2 是 MVP-1 的核心内容，「先跑通 1 家」跑通的其实是 seed，不是流程 |
| **§3.6 规格发布** | `version.ts` 的 `publishDraft`、`currentDraft`、`nextVersionNo` | **零个端点** | 公司无法建草稿、改价、发布新版本。改一次价要改代码重新部署 |
| **FR-1 结构化 mention token** | `routing/mention.ts` 的 `routeByToken` | 服务端只调 `parseMentions` + `routeByText` | 需求明确写「前端联想选择器选中后携带结构化 token」是**主路径**，文本匹配是**兜底**。现在兜底成了唯一路径 |
| **FR-3 视觉抽取** | `VisionExtractor` **接口** | **零个实现类** | FR-3 的主路径（图像理解/OCR）完全没实现，只有降级的手动录入。`createAppContext` 的 `vision` 永远是 `undefined` |
| **计费出账** | `billing/lead-events.ts` 的 `invoice` | 从未被调用 | 计费事件产生了，但永远不会进入 `invoiced` 状态。收不到钱 |

`routeByToken`、`blankTemplates`、`currentDraft`、`invoice` —— 这几个函数在
`src/` 里**被其他文件引用 0 次**，只有测试引用。测试通过给了"功能完成"的错觉。

### 2.3 需求描述与实现方式不一致

| 需求原文 | 实现 | 差距 |
|---|---|---|
| FR-4：「客户通过**对话**提修改意见触发局部重新生成」 | `/api/floorplans/:id/layout/regenerate` 需要客户端显式传 `wallRunId` | 从"对话里说一句"到"调用带参数的端点"之间没有桥。场景 D 第 4 点描述的交互不存在 |
| FR-3：「解析结果必须覆盖所有相关区域，不允许漏项」 | 手动录入路径下，客户可以只补墙长就 `ready=true` | 窗户/上下水/家电位不补也算就绪——刚补的 `addFeature` 端点是可选的，没有任何提示告诉客户"不补就排不出水槽" |
| 场景 A：公司入驻走对话式录入 | 无端点 | 见 2.2 |

## 3. 建议的优先级

### P0 —— 挡住"能不能真的用起来"

1. **FR-2 入驻端点 + §3.6 发布端点**。没有这两组，平台**无法接入第三家公司**。
   这是目前离"能跑业务"最远的一块，而且库函数已经齐了，主要是接线与权限。
   工作量：中（要设计公司侧的会话状态与草稿工作流）。
2. **计费出账接线**（`invoice`）。现在计费事件只进不出，收入链路是断的。
   与 G4 费率定案一起做。

### P1 —— 影响质量与可信度

3. **FR-3 视觉抽取的真实实现**。现在整个户型录入是手动的，
   客户上传一张图什么也不会发生。有了 FR-1.2 的 `vision` 层配置，接一个多模态调用即可。
   注意保持「读取 + 标注不确定，不做决定」的定位。
4. **对话 → 局部重排的桥**。客户说"把水槽挪到窗下"应该能直接触发重排，
   而不是让他去点"重新排布这段墙"。FR-1.2 的 `layoutRevision` 调用点就是为这个准备的，
   但还没有从自然语言解析出"改哪段墙、怎么改"的那一步。
5. **户型完整性提示**。`isLayoutReady` 只看墙长和层高。应当在没有上下水时
   明确告诉客户"没有水槽位置信息，这一版不会有水槽柜"——现在是静默地排出一版没水槽的方案。
6. **结构化 mention token**。接上主路径，文本匹配退回兜底。

### P2 —— 打磨

7. `missingFields` 的关键词表太窄（"质感""深色"匹配不到"风格"）。
   已经用"重复提问就改口给选择题"缓解了，但根子上应该让选择题成为主路径。
8. 供给侧没有任何界面。`web/index.html` 全是需求侧的。
9. 测试文件 23 个 / 源文件 56 个，覆盖不错但**集中在纯函数**；
   端到端只有 `http.test.ts`。这次的三个 bug 都是模拟跑出来的，不是单测抓出来的——
   建议把 `scripts/simulate.mts` 纳入 CI 做冒烟。

## 4. 一个方法论上的收获

这次审查里，**跑一遍端到端模拟比读代码有效得多**。三个 bug（缺特征入口、组装偏好
整单被拒、助手原地打转）都不是单元测试能发现的——每个模块的测试都是绿的，
问题出在**模块之间的接线**和**真实数据流经它们时的组合行为**。

而"库函数齐全但没接端点"这类问题，连模拟也发现不了（模拟只走已有的端点）。
它需要的是**拿需求文档逐条对端点清单**——本次审查 2.2 节的五项都是这么找出来的。

两种方法互补：模拟查"接了的地方对不对"，逐条比对查"该接的地方接没接"。
