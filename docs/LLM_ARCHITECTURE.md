# LLM 模型分层

> 后端用三层模型：**轻量（对话）/ 主力（推理）/ 视觉（户型图）**。
> 这份文档说明为什么这么分、什么时候升级、以及三条不因分层而放松的约束。
>
> 实现：`src/agents/model-tiers.ts`

---

## 1. 为什么要分层

对话轮次是这个系统里最主要的模型成本项。客户跟总控助手来回聊十几轮，最后才出一次方案。
这十几轮里绝大部分是「收集需求、答一句常识、澄清一个字段」——用最强的模型去做，
贵，而且慢（客户正在等回复）。

但**有些时刻确实需要强模型**：

- 把一段自然语言的修改要求翻译成对多个约束的调整（"把水槽挪到窗下，但洗碗机别动"）；
- 从一份格式混乱的价目表里抽出结构化规格（FR-2 的降级路径）。

这些做错了，后果是**错的方案和错的报价**，而不是"客户再问一遍"。

## 2. 三层的分工

| 层 | 环境变量 | 干什么 | 特点 |
|---|---|---|---|
| 轻量 `chat` | `LLM_MODEL_CHAT` | 总控助手日常问答、需求收集、澄清、术语解释、公司规格事实问答 | 高频、延迟敏感、单轮价值密度低 |
| 主力 `reasoning` | `LLM_MODEL_REASONING` | 需求 → 设计意图、复杂修改理解、规格模板解析 | 低频、错了代价大 |
| 视觉 `vision` | `LLM_MODEL_VISION` | 户型图抽取（FR-3） | 多模态，文本模型做不了 |

### 调用点登记

所有会调用模型的地方都在 `CallSite` 里登记，不散落字符串字面量：

| 调用点 | 层 | 为什么 |
|---|---|---|
| `orchestratorChat` | 轻量 | 答错一句常识，客户再问一遍就好 |
| `companySpecQa` | 轻量 | 上下文里已经把规格清单摆在眼前，是事实问答不是推理 |
| `designIntent` | 主力 | 需求 → 选型，错了整版方案都是错的 |
| `layoutRevision` | 主力 | 多约束修改，容易顾此失彼 |
| `specTemplateParse` | 主力 | 错了整批型号的规格都是错的 |
| `floorPlanExtract` | 视觉 | 输入是图 |
| `designCritique` | 主力 | 运营侧 DesignCritic（FR-21）；无 key 确定性降级 |

平台训练抽卡（FR-22）MVP 走确定性 `extractKnowledge`；有 LLM 时可挂轻量层，不进客户断言路径。

分配依据是**「错了的代价」**，不是「看起来难不难」。

---

## 3. 视觉模型：需要，而且已经在架构里了

**结论：需要。** 但问题不是「要不要第三个模型」，而是**怎么定位它**。

户型图是图片或 PDF，要从中读出墙段长度、门窗位置、上下水、层高——这是纯多模态任务，
文本模型无从下手。所以视觉模型不是可选的锦上添花，它是 FR-3 的必要条件。

### 定位：读取 + 标注不确定，**不做决定**

视觉模型的输出**一律不自动采用**：

- 抽取结果进 `RawExtraction`，字段**全部可选**——模型看不清就该留空，而不是编；
- 置信度低的项进 `FloorPlanUnresolved`，`suggestion` 字段**仅供展示，永不自动采用**；
- `isLayoutReady` 为假时，出方案接口直接 409 并列出待办项。

理由很实在：**尺寸读错 3 英寸，出来的是一份装不上墙的方案和一份错的报价**，
而这个错误要到安装当天才会暴露。让客户"自己发现不对再反馈"，是把成本转嫁给
最没有能力发现问题的一方。

### 视觉层**不回退**到文本模型

其他两层之间可以互相回退（轻量没配就用主力，只是贵）。视觉层**刻意不回退**：

```
没有多模态模型 → 户型录入降级为手动逐项确认（FR-3 已支持）
```

而不是把图交给一个看不见图的模型去猜。启动日志会明说这一点。

---

## 4. 什么时候从轻量升到主力

### 核心原则：确定性触发为主，模型自述为辅

**不能全靠轻量模型自己举手说"我需要升级"。** 它判断力不足的时候，恰恰就是最需要
升级的时候——这是个自指的陷阱。

判断顺序（`escalationDecision`）：

| 优先级 | 触发条件 | 类型 |
|---|---|---|
| 1 | 正在做规格模板解析 | 确定性 |
| 2 | 户型图刚解析完，要逐项核对 | 确定性 |
| 3 | 客户要求出方案/报价 | 确定性（正则） |
| 4 | 修改要求涉及 ≥2 个部位且含转折词 | 确定性（正则） |
| 5 | 轻量模型自己举手 | 模型信号（辅助） |
| 6 | 连续 3 轮没有新信息被收集 | **兜底** |

第 6 条是兜底：轻量模型可能在原地打转，客户已经说了三轮却一个字段都没被收集到。
判据是**需求摘要有没有变长**（`mergeRequirements` 只在真有新内容时才追加），
比让模型自述可靠。

### 多约束修改的识别

```
"水槽往左挪一点"                    → 单约束，不升级
"水槽和灶台都在这面墙"               → 陈述句，无转折，不升级
"把水槽挪到窗下，但是洗碗机别动"       → 2 个部位 + 转折 → 升级
```

轻量模型处理最后一句时容易漏掉后半句，客户会拿到一版洗碗机被挪走的方案。

## 5. 三条不因分层而放松的约束

1. **FR-8 照旧**：哪一层模型都不产出价格。价格只由 `PricingEngine` 从规格库算。
   模型输出里的任何金额字段都会被 `stripPriceFields` 白名单丢弃。
2. **`@` 路由永远是确定性的**（FR-1）：哪家公司由归一化精确匹配决定，
   不经过任何模型。模型只负责"说什么"，不负责"这是哪家公司"。
3. **升级判断有确定性兜底**：见上一节。

分层是**成本与延迟**的优化，不是把安全边界也一起分层。

---

## 6. 降级路径

| 情况 | 行为 |
|---|---|
| 三层齐全 | 正常 |
| 轻量层缺失 | 回退主力（贵一点，不影响正确性） |
| 主力层缺失 | 回退轻量，**启动日志明确警告准确度下降** |
| 视觉层缺失 | 户型录入降级为手动逐项确认，**不回退到文本模型** |
| 只配了 `OPENAI_MODEL` | 文本两层都用它（向后兼容单模型部署） |
| 一个都没配 | 对话降级为确定性引导问答；**报价、闸门、计费完全不受影响** |

最后一条是刻意的：核心链路（定价、发送闸门、计费、租户隔离）里没有任何一步依赖模型，
所以没有 API key 的环境也能端到端跑通完整流程。这也是测试能覆盖全链路的原因。

## 7. 配置示例

```bash
# 轻量层：跑 90% 的对话轮次
LLM_MODEL_CHAT=claude-haiku-4-5-20251001

# 主力层：需求→方案、复杂修改、规格解析
LLM_MODEL_REASONING=claude-opus-5

# 视觉层：户型图抽取
LLM_MODEL_VISION=claude-opus-5
```

### 7.1 测试用户 / `pnpm simulate` 专用（不影响生产）

模拟里的 **user agent** 与 **场景生成** 走独立端点，默认本机 Ollama；**不读**
生产 `OPENAI_API_KEY` / `LLM_MODEL_CHAT`。simulate 上传户型图时，若配置了
`LLM_MODEL_TEST_VISION`，视觉抽取也改用测试视觉（不改生产 `OPENAI_BASE_URL_VISION`）。

```bash
OPENAI_API_KEY_TEST=ollama
OPENAI_BASE_URL_TEST=http://localhost:11434/v1
OPENAI_BASE_URL_TEST_VISION=http://localhost:11434
LLM_MODEL_TEST_CHAT=qwen2.5:14b-instruct
LLM_MODEL_TEST_REASONING=qwen2.5:14b-instruct
LLM_MODEL_TEST_VISION=qwen2.5vl:latest
```

装配入口：`createTestLlmClient()` / `createVisionExtractorFromTestEnv()`。

启动时会打印实际生效的分层与回退情况：

```
[rta-hub] LLM 分层：
[rta-hub]   · 轻量(对话)：claude-haiku-4-5-20251001
[rta-hub]   · 主力(推理)：claude-opus-5
[rta-hub]   · 视觉(户型图)：claude-opus-5
```

## 8. 为什么不用 `@meso.ai/let-it-flow` 的 CallSite 体系

let-it-flow 的 `CALL_SITES` 是一个**固定枚举**，面向他们自己的内容产品
（`planner` / `rewrite` / `podcast_skill_agent` 之类）。我们的调用点——户型抽取、
规格模板解析、公司 Agent 问答——一个都不在里面。硬塞进去只会让语义对不上，
以后读代码的人还要先搞清楚"为什么户型抽取叫 image_prompts"。

所以这里维护自己的层级映射，用 `llm.modelById()` 取模型——那是个不带语义假设的入口。
分层配置没给出模型 id 时，仍然回退到 let-it-flow 的 `writer` 角色，
它自己的配置体系照常管用。
