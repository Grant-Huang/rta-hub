## 2. 采集：把家电当成客户提供的输入，不是常数

### 2.1 为什么必须问

写死 36" 的冰箱位有两个问题：

1. **装不下。** 客户的冰箱是 36" 宽 + 两侧各 1" 的通风间隙 = 38"，按 36" 留空
   就塞不进去。反过来，客户是 30" 的窄冰箱，留 36" 就白白浪费 6" 的储物。
2. **位置也是客户定的。** 现在冰箱位靠"有没有强电特征"来推——没有强电特征就
   **根本不放冰箱**。这既不合理（谁家厨房没冰箱），也不是客户的意思。

家电是客户**已经拥有或已经选定**的东西。它是输入，不是我们替他决定的。

### 2.2 问什么

作为 FR-1.1 的选择题增加一组（**不是开放式提问**）：

```
▸ 厨房里会有哪些家电？（多选）
   □ 冰箱      □ 灶台/炉具   □ 烤箱（独立）
   □ 抽油烟机  □ 洗碗机      □ 微波炉

▸ 冰箱的宽度？
   · 30"（窄款）          · 33"（常见）  [常见选择]
   · 36"（对开门/法式）    · 我去量一下再说
   · 其他（填写）
   说明：两侧各留 1" 通风，柜位会按你的尺寸 +2" 预留。

▸ 冰箱想放在哪？
   · 靠近入口（进门先放东西）  [常见选择]
   · 靠近水槽
   · 我不确定，你帮我定
   说明：冰箱把手一侧需要 ≥15" 的落台面，位置会影响整体排布。
```

设计原则与 FR-1.1 一致：

- **给选项、给常见值、给"我不确定"**。客户多半不知道自己冰箱多宽，逼他量了
  才能继续是把系统的困难转嫁给他。
- **每个选项说清它影响什么**（尺寸影响留空，位置影响落台面）。
- **"我不确定"是合法答案**，走默认值，但**在图纸解释里如实标注**：
  「冰箱位按 33" 常见尺寸预留。如果你的冰箱更宽，这一版要调整。」

### 2.3 数据结构

```ts
export type ApplianceKind =
  | "refrigerator" | "range" | "cooktop" | "wallOven"
  | "rangeHood" | "microwave" | "dishwasher";

export interface ApplianceSpec {
  kind: ApplianceKind;
  /** 客户给的宽度（英寸）。未提供时用 defaults 并标注为推定值。 */
  width?: number;
  height?: number;
  depth?: number;
  /** 两侧通风/门缝间隙，加在 width 上得到实际留空。 */
  clearanceEachSide?: number;
  /** 客户希望放的位置。deterministic 的排布器会尽量满足，满足不了要说明。 */
  preferredZone?: "nearEntry" | "nearSink" | "nearWindow" | "any";
  /** 这个尺寸是客户给的还是我们推定的——解释里要说清楚。 */
  provenance: "customer" | "assumed";
}
```

`provenance` 这个字段是本设计的重点之一：它让「我们假设了什么」变成**数据**，
而不是散落在文案里的一句话。图纸解释、报价备注、发给商家的资料都要读它。

**实现记录（M5-3）**：数据存在 `FloorPlan.appliances` 上而不是偏好里——
家电是**这个厨房的物理事实**，不是对某家公司的选择；贸易账号一个人有多个项目，
挂在偏好上就串了。`provenanceNote()` 与 `violationCaveat()` 分开两个函数，
因为用途不同：前者任何时候都该说，后者**只在方案被否决时**才有意义——
「你的厨房排不下」和「按我们猜的尺寸排不下」对客户是完全不同的两句话。

## 3. 配套柜 —— 家电不只是一段空白

现在家电位是"这段墙不能放柜子"。但真实厨房里，家电周围**有专门的柜子**：

| 家电 | 配套柜 | 说明 |
|---|---|---|
| 冰箱 | **冰箱上柜**（wall，深 24"、高 12–18"） | 比普通吊柜深，与冰箱齐平；不做的话冰箱顶上是一个积灰的空当 |
| 冰箱 | 两侧**收口板**（深 24" 通高） | 冰箱侧面外露，要贴板 |
| 抽油烟机 | **烟机上柜**（wall，中间掏空或整体让位） | 烟机占吊柜层，两侧才是柜 |
| 独立烤箱 | **烤箱高柜**（tall，中间开洞） | 单烤/双烤开洞高度不同 |
| 微波炉 | **微波柜** 或 与烟机二合一 | |
| 灶台（嵌入式） | **灶下柜**（台面开孔，抽屉要避让） | 不能用普通三抽柜——上层抽屉会顶到灶 |
| 洗碗机 | 无柜（纯空位），但**需要相邻水槽** | 已有 NKBA 检查 |

### 3.1 这就是 §2 能力标签的用武之地

排布器不该写 `if (code.startsWith("RFW"))`。它该问规格库：
**「给我一个 servesAppliance === "refrigerator" 且 roles 含 applianceHousing 的
吊柜型号」**（见 `CATALOG_MODEL.md` §2）。

有的商家有冰箱上柜，有的没有。没有的时候：

- **不静默跳过**——冰箱顶上留空当是个真实的、客户会看见的结果；
- 在 warnings 里报出「这家没有冰箱上柜型号，冰箱顶部会留空当」，
  由客户决定是接受还是换一家。

这与 BOM 缺辅料型号时的处理一致（`bom.ts` 的 `missing`）。

**实现记录（M5-6）**：`planApplianceCabinets()`（`layout/generate.ts`）+ `bom.ts` 的
冰箱侧收口板。写的时候撞到四件事，都不是"多排一个柜子"那么简单：

1. **配套柜要先于吊柜装箱算好。** 冰箱上柜可能**比冰箱位本身宽**——33" 的冰箱
   留 35" 的位，而这家最小的冰箱上柜是 36"。只按冰箱宽度让位的话，上柜会与
   旁边那个普通吊柜叠在一起（几何自洽审核第一次跑就抓到了这条）。
   要占多宽，得先算出来再让开。
2. **配套柜不能参与通用装箱。** 冰箱上柜的 `type` 也是 `wall`，于是装箱器
   把它当普通吊柜排到了墙的另一头——一版方案里出现了 4 个冰箱上柜。
   判据是能力（`servesAppliance` 非空 = 专用件），不是 `type`。
3. **嵌入式灶台下面有柜子。** 它是掉进台面的一个洞，不是一段没有柜子的空白。
   而且那个柜子要**顶部开放**：普通地柜最上面那一格是抽屉，会顶到灶体。
   `F7_FALSE_FRONT_DOUBLE`（假抽面 + 双门）正是这个构造——所以水槽柜箱体
   同时具备 `cooktopBase` 能力，不是巧合：两者要的都是"上面那一格是空的"。
   顺带修了两处**尺寸假设**：灶台占的墙宽是**柜子的宽度**（每侧 +1.5"），
   不是灶的宽度；开孔切到柜体侧板就废了。
4. **"按 SB 码认水槽"这时候会咬人。** 灶下柜用的就是 SB 箱体，于是工作三角里
   出现了两个水槽点、一个灶点都没有——而且不报错。三处按码兜底的地方
   （`ergonomics`/`aesthetics`/`explain`）都补上了「排除配套给家电的那些」。
   这是 M5-2 那条原则的又一次验证：靠字符串猜语义，换个上下文就崩。

冰箱侧收口板单独算一条，用的是**通高**板（84"）：冰箱比两边的柜子高，
常规地柜收口板只盖得住下面 34.5"，上面半截仍然是白色刨花板边。
贴着内墙角的那一侧不算——那侧对着墙。这家没有够高的板就记进 `missing`，
不拿一块 34.5" 的板顶上去充数。

### 3.2 吊柜层要知道地柜层的家电位置

抽油烟机在吊柜层，但它的位置由**灶台**决定，而灶台在地柜层。现在两层是分开排的，
吊柜层完全不知道灶在哪。

改法：家电位置在**分层排布之前**统一确定（它本来就是全局约束），
两层都读同一份 `reserved` 列表。

**实现记录（M5-4）**：`src/layout/appliance-plan.ts`。实现时撞到三件事，
都是「硬约束只在事后打分」的同一个病根：

1. **默认放冰箱之后，冰箱压在了上下水上**——排布器随后发现"没有需要放水槽的
   子段"，整套厨房就没有水槽了，而且不报错。修法是给水槽**连同两侧台面**
   （36 + 24 + 18）预留一块，家电不能占。
2. **灶台被顶到墙角**，落台区 0"，随后被自己的检查器否掉。修法是把 NKBA 的
   落台区要求写进落位的可行性判断——与 v0.6 修水槽落位是同一个教训。
3. **落台区不能跨过门洞**。只看到墙尽头的距离会得出「左侧有 129 寸」，
   而实际上灶台左边 1 寸就是门洞。所以占位分成两类：门洞/家电是**硬断点**
   （台面在这里断掉），给水槽预留的那块是**软占位**（家电不能占，但它就是台面，
   落台区可以延伸过去）。混作一谈会把水槽区当成断点，得出错误的否决。

另外修掉一条**过严的规则**：原来"填缝条只放墙角"，于是夹在冰箱与灶台之间的
那段墙一条填缝条都放不了，装箱剩下的 1" 成了真实的缝，台面连续性断掉。
紧挨家电的那一头也是合法填缝位——那里的门缝节奏本来就被家电打断了。

## 4. 标注：图上必须能看出哪个是什么

### 4.1 硬性要求

**每一张图**（全局俯视图地柜层/吊柜层、正视图、单墙俯视图、侧视图）上：

1. **水槽**必须画出**水槽轮廓本身**（不只是给柜体填个色），并标注 `水槽`；
2. **每个家电位**必须有文字标签（`冰箱 33"`、`灶台 30"`、`洗碗机 24"`）；
3. 标签放不下时（柜位太窄）用**编号 + 图例**，不是省略。
   省略等于图上有一个客户看不懂的方块。

### 4.2 水槽必须画在 SB 柜上

用户明确指出：**水槽应该落在 SB 的柜子上面**。

现在的实现里，水槽柜 `SB36` 是被正确选出来的（`sinkModules` 过滤
`type === "sinkBase"`），位置也正确。缺的是**图上的水槽盆轮廓**：俯视图上
应当在水槽柜的台面范围内画一个（或两个，双盆）圆角矩形 + 龙头位置。

这不是装饰。客户看俯视图时判断的是"洗碗的时候我站哪、左右够不够放东西"，
一个没画盆的柜子回答不了这个问题。

### 4.3 图例

每张图右下角固定一块图例：

```
■ 地柜   ■ 吊柜   ▨ 家电位   ▧ 填缝条   ◍ 水槽
```

图例是**从图上实际出现的元素生成的**，不是写死的一段 HTML——
没有吊柜的图不该有"吊柜"图例。这与 `explain.ts` 的原则一致：
**说的每一句都要对应实际算出来的东西**。

## 5. 排布算法要跟着改的地方

| 位置 | 现在 | 要改成 |
|---|---|---|
| `APPLIANCE_CLEARANCE` | 三个常数 | 从 `ApplianceSpec.width + 2×clearanceEachSide` 算；无客户数据时用常数并标 `provenance: "assumed"` |
| `splitIntoSegments` | 只对有对应特征（燃气/强电）的家电留空 | 客户声明了就要留，没有特征时按 `preferredZone` 与人体工程求位置 |
| 家电种类 | `refrigerator / range / dishwasher` | 加 `wallOven / rangeHood / microwave / cooktop` |
| 分层 | 地柜、吊柜各自排 | 家电位先全局确定，两层共用 |
| 配套柜 | 无 | 家电位确定后，按能力标签补配套柜与收口板 |

## 6. 对现有硬约束的影响

NKBA 检查（`ergonomics.ts`）现在按写死的家电宽度算落台区。改成读 `ApplianceSpec`
之后，**同一个户型在不同家电尺寸下会有不同的结论**——这是对的，也正是要的。

需要注意：`provenance: "assumed"` 的家电产生的硬约束违规，在提示里要区别对待：

> ✗ 灶台两侧落台区不足（现为 12"/10"）
>   注意：灶台宽度按 30" 推定（你还没提供实际尺寸）。如果你的灶更窄，这一条可能不成立。

**推定值导致的否决必须说明它是推定的。** 否则客户会以为自己的厨房真的排不下。

## 7. 测试场景（要加进模拟器的场景生成器）

| 场景 | 覆盖点 |
|---|---|
| 客户给了全部家电尺寸 | 留空按实际尺寸；标注显示真实数字 |
| 客户全选"我不确定" | 走默认值；**图纸解释里必须出现"按 XX 推定"** |
| 36" 冰箱塞进 90" 的墙 | 留空后剩余不足，硬约束否决 + 说明是实测值不是推定 |
| 商家没有冰箱上柜型号 | warnings 报出，不静默 |
| 有抽油烟机 | 吊柜层在灶台正上方让位；两侧仍有柜 |
| 独立烤箱 | 排出烤箱高柜，且高柜不与吊柜重叠 |
| 嵌入式灶台 | 灶下柜不能是普通三抽柜 |
