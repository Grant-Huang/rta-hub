## 1. 拆解原则

MVP-1 的目标是"用 1 家真实公司把规格 → 对话 → 报价 → 确认发送 → 计费这条链路完整跑通"。
按**风险 × 规格完备度**排序施工：

| 优先级 | 判据 | 对应模块 |
|---|---|---|
| 最高 | 错了会直接产生对外的错误金额 | 定价引擎、Money、FR-8 校验 |
| 高 | 以后再补代价极大（数据迁移） | 规格版本化、报价快照、租户隔离 |
| 高 | 合规/安全底线 | 发送闸门、鉴权、发送前披露 |
| 中 | 规格明确、可独立测试 | 脸型文法、@ 路由、计费去重与争议 |
| 后置 | 依赖上面全部就绪 | LLM 编排、户型图、EstimateDraft |

**为什么先做定价而不是先做对话**：对话层是可替换的外壳，定价层是不可替换的地基；
而且定价是纯函数、可穷举测试，能在没有任何 LLM 调用的情况下建立正确性基线。

- **装箱**：恰好整除无剩余；同填充度下柜子更少者胜出（72" → 2×36 而不是 6×12）；

## 4.1 排布质量：三类约束分开处理（MVP-2 补强）

初版 FR-4 的目标函数只有「填得满、柜子少」——这只覆盖了**造价与安装**，
漏掉了**使用方便**与**美观**。而且这两者不是同一类东西：

| 类别 | 例子 | 处理方式 | 违反后果 |
|---|---|---|---|
| **硬约束**（安全/人体工程）| 灶台旁没有落台区、洗碗机离水槽 >36" | `ergonomics.ts`，**不参与权衡** | 否决方案，不允许出报价 |
| **软约束**（美观）| 宽度跳动、凑数窄柜、填缝条在中间 | `aesthetics.ts`，进目标函数 | 扣分，仍可下单 |
| **成本** | 柜体数量、浪费长度 | `pack.ts` 的代价项 | 扣分 |

**为什么硬约束不能靠权重平衡**：权重再高也可能被一个足够便宜的方案压过去。
灶台旁没处放热锅不是"省了两百加币"能换的。

### 目标函数的实际改动

DP 状态里加上「上一个柜宽」，把**宽度节奏**与**窄柜惩罚**直接编进代价，
而不是事后再挑。状态规模仍是 O(L × |W|)。效果：

| 墙长 | 旧目标（填满 + 柜少） | 新目标 |
|---|---|---|
| 78" | `36, 33, `**`9`** | `27, 27, 24` |
| 87" | `36, 36, `**`15`** | `30, 30, 27` |
| 93" | `36, 36, 21` | `33, 30, 30` |

旧版为了"柜子最少"会塞一个 9" 柜——储物几乎没用、单位造价最高、正视图上最扎眼。

### 其他补强

- **水槽对齐窗中心**，左右两段分别装箱，避免被装箱算法挤走。
- **洗碗机自动落在水槽旁**（NKBA ≤36"）。
- **高频区（灶台/水槽旁）偏向抽屉柜**——偏好进**装箱**阶段，
  否则装箱先定下 21" 而公司的抽屉柜只有 24"/30" 就白搭。
- **吊柜柜缝对齐地柜**：把地柜缝位置作为 DP 的对齐奖励点。
- **功能性窄柜是打折不是免罚**：一个 9" 调味品拉篮柜可以，一整排不行。
- 填缝条只放墙角；夹在柜子中间会打断门缝节奏。

### 实现中发现的缺陷

- **硬约束检查本身有 bug**：`landingAround` 已排除水槽柜，代码又减了一次
  `sink.width`，重复扣减导致合格方案被误判。生成的方案违反自己的硬约束才暴露出来。
- 水槽识别靠 `moduleCode.includes("SB")`，第二家公司用 `NW-SK36` 就认不出。
  改为优先看排布器打的 `label`，与「@ 路由不靠猜」是同一条原则。
- `explainCost` 漏了 `preference` 项——它参与了 DP 决策却不出现在代价明细里，
  无法解释"为什么选了这一版"。

### 5.1 PDF：为什么自己写而不是引库

立面图的几何**本来就在手上**——`Placement` 携带绝对英寸坐标。引 SVG→PDF 的转换库，
等于把已经算准的坐标再过一道栅格化/单位换算，引入误差和一个 MB 级依赖，换来的只是
"少写一个 PDF 写入器"。所以直接把几何写成 PDF 矢量指令：多页、文本、线框、base-14 字体，
够用且可控。

一个如实记下的边界：base-14 字体是 Latin-1，画不出中文。中文墙段标签在 PDF 上会译成英文
（`北墙` → `North Wall`，译不出的退到 `Wall N`），**不会留 `??`**；其余画不出的字符
一律进 `warnings` 上报，不静默丢字。

### 5.2 贸易价：门槛落在定价链路上

开放问题 7 的定案是"人工核实 + 有效订阅"。关键不在于定了哪两道门槛，而在于**门槛写在哪**：

```ts
// src/trade/verification.ts
effectiveAccountType(account, verification)  // 未过门槛的 trade → "consumer"
```

报价生成时用的是 `effectiveAccountType` 而不是 `account.accountType`，所以绕过界面直接
打 API 也拿不到贸易价。如果只在界面上隐藏贸易价，这条防线等于不存在。

降级时响应里带 `tradePricing: { applied: false, reason, nextStep }`——如实说明为什么按
零售价出单、下一步该做什么，不静默降级。

### 5.3 方案持久化：三张表的语义不同

| 表 | 语义 | 写入方式 |
|---|---|---|
| `StoredLayout` | 当前工作态，同一 (户型, 公司) 一条 | 覆盖更新 |
| `DesignLayout` | 方案标识，承载 `specVersionId` | 覆盖更新 |
| `DesignRevision` | 修订链 | **只追加**（§3.6） |

`Quote` 与它们都不同：一经确认即不可变，是对外承诺的凭据。方案会反复重算，报价不会。
报价创建时引用方案的**真实修订号**，所以事后能回答"当时发出去的是哪一版"。

### 5.4 争议裁定台带证据，不凭一面之词

`/api/admin/disputes` 返回的不只是争议本身，还有该报价的**审计事件链**与
`snapshotIntact` 标记——比对当前报价内容的哈希与发送时刻记录的哈希是否一致。

注意这里比的是**内容哈希**而不是"拿当前规格复算"：公司发布新规格版本后本来就会算出不同的价，
那不是篡改。用复算去判篡改会产生大量假阳性。

### 5.6 价格与偏好的选择式提问（FR-1.1）

原来对预算和偏好是开放式提问的。问题在于**客户不是行业内人士**——"你的预算是多少"这个问题，
等于要求客户先自己做一遍市场调研。改成给选项 + 给算出来的价格影响。

实现上有三个地方值得记一笔：

1. **价格组溢价只在公共型号上算**（`priceGroupPremiums`）。价格矩阵允许有洞，两组各自求平均
   再相比等于拿两个不同的篮子比总价。交集为空时返回「价格待确认」而不是硬给一个数。
2. **偏好按「跨公司 / 公司专属」分开存**。门板/五金/配件 id 换公司就失效；预算档位、储物偏好
   跨公司保留——否则比价时两家用的是两套不同偏好排出来的方案。
3. **储物偏好进的是排布算法**（`LayoutOptions.drawerBias`），不是记下来展示。选"尽量多做抽屉"
   会改变装箱候选的 `preference` 项：144" 的墙从 `B36×4` 变成 `3DB24 + 3DB30×4`。

### 5.7 上线闸门、图纸解释、LLM 分层

三块相对独立的补强：

**上线闸门**（`src/app/launch-gates.ts` + `docs/LAUNCH_BLOCKERS.md`）——
把「上线前必须核实的事」从文档搬进代码。判断哪些阻断启动的标准是**「错了会不会
安静地产出错误的对外结果」**：税率、NKBA 净空、鉴权、线索费率会 → 阻断；
`GenericCatalog`（代码已如实降级标注）、留存 cron（不产出错误结果）→ 只告警。
声明用**核实日期**而非 `true`，过了复核周期自动变回待办。

**图纸解释**（`src/render/explain.ts`）—— 四视图对客户是陌生的表达形式，
没有解释他只能说「感觉怪怪的」，说不出哪里怪，修改意见就无从提起。
一条硬规则：**解释必须来自实际算出来的结果**。有个真实的 bug 是测试抓出来的——
`renderRationaleText` 给条目做了 markdown 剥离却漏了 headline，纯文本里漏出 `**`。

**LLM 分层**（`src/agents/model-tiers.ts` + `docs/LLM_ARCHITECTURE.md`）——
轻量/主力/视觉三层。两个关键决定：视觉层**不回退**到文本模型（看不了图就是看不了，
回退过去只会得到瞎猜的尺寸）；升级判断**确定性条件优先于模型自述**
（模型判断力不足时恰恰最需要升级，这是个自指陷阱），兜底是连续 3 轮没进展强制升级。

### 5.8 端到端模拟与对齐审查

新增 `pnpm simulate`（`scripts/simulate.mts`）：三套厨房（一字型/L 型/U 型）走真实
HTTP 端点跑完整链路，产出四视图与解释。**它一跑就抓到三个单测抓不到的 bug**：

1. 客户没有任何入口补充窗户/上下水位置 → 没有视觉模型时**每套厨房都排不出水槽柜**。
   `addFeature` 函数早就写好了，只是没接端点。
2. 组装偏好套到只提供 RTA 的吊柜上 → **整单报价 422**，客户只看到"校验未通过"。
3. 助手连着三轮问同一个问题（客户答了但说法对不上关键词表）。

逐条比对需求与端点清单又发现一类更隐蔽的问题：**库函数齐全、测试也有，但没接线**——
FR-2 入驻、§3.6 规格发布、FR-1 结构化 mention token、FR-3 视觉抽取、计费出账，
五项都是这样。详见 [DESIGN_REVIEW.md](./DESIGN_REVIEW.md)。

还修了一处真实的安全漏洞：公司侧端点没有鉴权，`TenantScope` 拿的是调用方自己填的
companyId。**租户隔离的前提是先证明你是谁，再按你的身份过滤；顺序反了，过滤只是装饰。**
